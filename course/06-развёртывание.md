# Лекция 6. Развёртывание: Docker, Compose и эксплуатация

## 6.1. Зачем контейнеры

Без них запуск проекта выглядит так: поставьте Python нужной версии,
PostgreSQL, создайте базу, пользователя, поставьте пакеты, пропишите пути…
На другой машине половина шагов сработает иначе.

**Контейнер** — коробка, в которой лежит программа вместе со всем окружением:
нужной версией Python, библиотеками, настройками. Коробка запускается
одинаково на любой машине с Docker.

Два понятия, которые путают:

- **Образ** (image) — шаблон, «слепок» файловой системы. Только для чтения.
- **Контейнер** (container) — запущенный экземпляр образа. Их может быть много
  из одного образа.

Аналогия: образ — класс, контейнер — объект.

Контейнер **не** виртуальная машина: он использует ядро хоста и потому
стартует за секунды и почти ничего не весит сверх самой программы.

## 6.2. Dockerfile — рецепт образа

```dockerfile
FROM python:3.12-slim

WORKDIR /srv
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app
COPY scripts ./scripts

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

Построчно:

- `FROM python:3.12-slim` — базовый образ. `slim` — урезанный, без лишних
  пакетов: меньше вес и меньше уязвимостей.
- `WORKDIR /srv` — рабочая папка внутри контейнера.
- `ENV PYTHONUNBUFFERED=1` — не буферизовать вывод, чтобы логи появлялись сразу.
- `COPY requirements.txt .` затем `RUN pip install` — **порядок важен**. Каждая
  инструкция создаёт слой, который кэшируется. Зависимости копируются отдельно
  от кода: правка кода не заставляет переустанавливать пакеты. Скопируй мы
  всё сразу — каждая правка означала бы полную переустановку.
- `EXPOSE 8000` — документирует порт (сам по себе ничего не открывает).
- `CMD [...]` — команда запуска.

`--host 0.0.0.0` обязателен: `127.0.0.1` внутри контейнера означает «только
внутри контейнера», снаружи достучаться не выйдет.

## 6.3. docker-compose.yml — оркестровка

Compose описывает несколько сервисов и их связи в одном файле.

```yaml
services:
  db:
    image: postgres:16-alpine
    container_name: abb-db
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-abb}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-abb}
      POSTGRES_DB: ${POSTGRES_DB:-abb}
    volumes:
      - ./db:/docker-entrypoint-initdb.d:ro
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5433:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-abb} -d ${POSTGRES_DB:-abb}"]
      interval: 5s
      timeout: 3s
      retries: 10
```

Разбор:

> **Где это в коде:** `docker-compose.yml:7` — сервис `db`;
> `docker-compose.yml:20` — его `healthcheck`; `docker-compose.yml:26` — сервис
> `api`; `docker-compose.yml:49` — профиль `full` у необязательных сервисов.

**`image` vs `build`.** Postgres берём готовым образом, API собираем из своего
Dockerfile (`build: ./api`).

**`environment`.** Переменные окружения внутри контейнера. `${VAR:-default}` —
взять из `.env`, иначе значение по умолчанию.

**`volumes`.** Два разных вида:

- `./db:/docker-entrypoint-initdb.d:ro` — **bind mount**: папка хоста видна
  внутри контейнера. `:ro` — только чтение. Правки на хосте сразу видны внутри.
- `pgdata:/var/lib/postgresql/data` — **named volume**: хранилище, управляемое
  Docker. Живёт независимо от контейнера. Именно поэтому данные не пропадают
  при `docker compose down` — и именно поэтому файлы из `db/` не применяются
  повторно (см. ниже).

**`ports: "5433:5432"`.** Слева порт хоста, справа порт контейнера. Postgres
внутри слушает 5432, наружу отдаём 5433, чтобы не конфликтовать с локально
установленным Postgres.

**`healthcheck`.** Команда проверки готовности. Без неё API стартует раньше
базы и падает на первом запросе.

```yaml
  api:
    build: ./api
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-abb}:${POSTGRES_PASSWORD:-abb}@db:5432/${POSTGRES_DB:-abb}
      REDIS_URL: ${REDIS_URL:-}
      WEB_DIR: /srv/web
    volumes:
      - ./api/app:/srv/app:ro
      - ./web:/srv/web:ro
      - ./db:/srv/db:ro
    depends_on:
      db: { condition: service_healthy }
    ports:
      - "8000:8000"
```

**`@db:5432`** — внутри сети Compose сервисы видны по именам. Никаких
IP-адресов: `db` — это имя сервиса, Docker резолвит его сам.

**`depends_on` с `condition: service_healthy`** — ждать не запуска контейнера,
а именно готовности базы (по healthcheck).

**Монтирование кода.** `./api/app:/srv/app:ro` означает, что правки в Python
подхватываются перезапуском контейнера без пересборки образа. То же для `web/`:
правка CSS видна после F5. В продакшене так не делают — код кладут в образ.

**Профили** — необязательные сервисы:

```yaml
  cache:
    image: redis:7-alpine
    profiles: ["full"]
```

```bash
docker compose up                    # только db + api (2 образа)
docker compose --profile full up     # ещё nginx и redis
```

Мы сделали это после того, как `nginx` не скачался из-за таймаута к Docker Hub:
чем меньше образов нужно тянуть, тем меньше поводов не запуститься.

## 6.4. Главная ловушка Postgres в Docker

```yaml
- ./db:/docker-entrypoint-initdb.d:ro
```

Файлы из этой папки выполняются **только один раз — при создании пустого
тома**. База уже существует → скрипты игнорируются молча.

Мы на этом потеряли время: добавили `03_search_index.sql`, перезапустили,
получили `column "search_name" does not exist`. Файл был на месте, но Postgres
его не выполнял.

Три способа жить с этим:

1. **Пересоздать том** (потеряв данные): `docker compose down -v && docker compose up`
2. **Накатить руками**: `docker compose exec -T db psql -U abb -d abb < db/03_search_index.sql`
3. **Применять при старте API** — наш путь, `ensure_schema()`. Требует
   идемпотентных миграций, зато нельзя забыть.

`-v` в `down -v` удаляет тома. Это необратимо.

## 6.5. nginx как обратный прокси

```nginx
server {
    listen 80;
    root /usr/share/nginx/html;

    location = /index.html {
        add_header Cache-Control "no-store, must-revalidate";
    }
    location / {
        try_files $uri $uri/ /index.html;
    }
    location /api/ {
        proxy_pass http://api:8000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

**Обратный прокси** — сервер, принимающий запросы и переправляющий их дальше.
Браузер обращается к одному адресу, а за ним стоят несколько сервисов.

Зачем: статику nginx отдаёт быстрее Python, а `/api/` и статика оказываются на
**одном origin** — тогда не нужен CORS.

**CORS** — правило браузера: страница с `localhost:8080` по умолчанию не может
обращаться к `localhost:8000`, это разные origin. Обходится либо заголовками
на сервере (`CORSMiddleware` у нас включён), либо тем, что всё живёт на одном
адресе — как здесь.

`try_files $uri $uri/ /index.html` — искать файл, потом папку, иначе отдать
`index.html`. Нужно для одностраничных приложений с маршрутизацией.

В базовом варианте nginx не нужен: FastAPI сам раздаёт `web/` через
`StaticFiles`, и всё живёт на 8000.

## 6.6. Команды на каждый день

```bash
docker compose up --build          # собрать и запустить, логи в терминале
docker compose up -d               # то же в фоне
docker compose ps                  # что запущено
docker compose logs -f api         # логи сервиса, -f = следить
docker compose restart api         # перезапустить один сервис
docker compose down                # остановить и удалить контейнеры
docker compose down -v             # ... и тома (данные пропадут!)
docker compose exec api bash       # оболочка внутри контейнера
docker compose exec db psql -U abb -d abb    # psql в контейнере
docker compose config              # итоговый конфиг с подставленными переменными
```

Последняя особенно полезна: показывает, какие **абсолютные** пути реально
монтируются. Так проверяется подозрение «а ту ли папку я запустил».

## 6.7. Диагностика: чему верить

Порядок действий, когда «не работает».

**1. Что вообще запущено**

```bash
docker compose ps
```

**2. Жив ли бэкенд**

```bash
curl -s localhost:8000/api/health
```

```json
{"status":"ok","db":true,"search_schema":true,"cache":false,
 "web_dir":"/srv/web","web_mounted":true}
```

Каждое поле отвечает на конкретный вопрос: база жива? миграции применены?
фронтенд смонтирован?

**3. Что реально отдаёт сервер**

```bash
bash tools/check_deploy.sh
```

Скрипт печатает содержимое `/srv/web/js` внутри контейнера, список
подключённых скриптов из отданного `index.html` и наличие ключевых правил в
CSS. Он отвечает на вопрос, который иначе решается гаданием: **старый код на
сервере или старая страница в браузере**.

**4. На месте ли правки в файлах**

```bash
python3 tools/verify_build.py
```

Ищет опорные фрагменты в css и js. Появился после случая, когда правка
«не применилась»: строка для замены не совпала, скрипт молча ничего не сделал.

**5. Кэш браузера**

Если сервер отдаёт новое, а на экране старое — `Cmd/Ctrl + Shift + R`.
Мы защитились двумя способами: `?v=` у ресурсов и `Cache-Control: no-store`
у HTML.

### Симптомы и причины из нашей практики

| Симптом | Причина |
|---|---|
| `{"detail":"Not Found"}` на `/` | фронтенд не смонтирован, `web_mounted: false` |
| `column "search_name" does not exist` | миграция не применилась к существующему тому |
| `TLS handshake timeout` при сборке | нет доступа к Docker Hub: прокси, зеркало или `docker save/load` |
| `Invalid HTTP request` в логах | curl с кириллицей в URL; нужен `--data-urlencode` |
| Интерфейс выглядит старым | кэш браузера или запуск из другой папки |
| Стиль «не применяется» | ниже в CSS есть второе правило с той же специфичностью |

### Демонстрация: что показывает `/api/health`, когда база падает

**Всё работает:**

```bash
curl -s localhost:8000/api/health
```

```json
{"status": "ok", "db": true, "search_schema": true, "cache": false,
 "web_dir": "/srv/web", "web_mounted": true}
```

```
$ поиск -> 200
```

**Останавливаем базу на ходу** (`docker compose stop db`) и повторяем:

```json
{"status": "degraded", "db": false, "search_schema": true, "cache": false,
 "web_dir": "/srv/web", "web_mounted": true}
```

В логах API при этом:

```
discarding closed connection: <psycopg.Connection [BAD] at 0x7f46b6fa9040>
```

**Как это читать.** `status` стал `degraded`, `db: false` — база недоступна.
Но `search_schema` и `web_mounted` остались `true`: это состояние, узнанное
при старте, оно не зависит от текущей доступности базы. Сервис отвечает,
отдаёт фронтенд и честно сообщает, что именно сломалось.

**Отдельное поведение — если база недоступна в момент запуска:**

```
psycopg_pool.PoolTimeout: pool initialization incomplete after 30 sec
```

API не поднимается вовсе. Это сознательный выбор: `db_pool.wait(timeout=30)`
в `lifespan` не даёт стартовать сервису, который заведомо не сможет работать.
Лучше упасть сразу и заметно, чем принимать запросы и отвечать на каждый
ошибкой. В Compose это дополнительно подстраховано `healthcheck` у базы и
`depends_on: condition: service_healthy` у API.

## 6.8. Переменные окружения

```bash
cp .env.example .env
```

```
POSTGRES_USER=abb
POSTGRES_PASSWORD=abb
POSTGRES_DB=abb
REDIS_URL=
```

Принцип: **конфигурация отделена от кода**. Один и тот же образ работает в
разработке и в проде, отличаются только переменные.

`.env` не кладут в репозиторий — там пароли. В репозитории лежит
`.env.example` с безопасными значениями-образцами.

## 6.9. Что изменить перед реальной эксплуатацией

Прототип и продакшен — разные вещи. Минимальный список:

1. **Пароли.** `abb/abb` заменить, хранить в секретах, а не в `.env` на диске.
2. **Код в образ.** Убрать `volumes` с кодом — иначе в проде поедет то, что
   лежит на диске сервера.
3. **Демо-данные.** Удалить `demo-data.js` и `withFallback` из `api.js`.
4. **HTTPS.** Сертификат на nginx.
5. **Аутентификация.** Её сейчас нет вовсе.
6. **Резервные копии.** `pg_dump` по расписанию, и обязательно проверенное
   восстановление — бэкап, который не восстанавливали, не бэкап.
7. **Несколько воркеров.** `uvicorn --workers 4` на 6-ядерной машине.
8. **Мониторинг.** Внешняя проверка `/api/health` и сбор логов.

## Проверьте себя
Ответы скрыты — сначала попробуйте сформулировать свой.

**1. Чем образ отличается от контейнера?**

<details>
<summary>Показать ответ</summary>

Образ — неизменяемый шаблон файловой системы (класс). Контейнер — запущенный экземпляр образа (объект). Из одного образа можно запустить много контейнеров.

</details>

**2. Почему `COPY requirements.txt` идёт до `COPY app`?**

<details>
<summary>Показать ответ</summary>

Каждая инструкция Dockerfile создаёт кэшируемый слой. При таком порядке правка кода не приводит к переустановке зависимостей — пересобирается только последний слой.

</details>

**3. Что произойдёт после `docker compose down -v`?**

<details>
<summary>Показать ответ</summary>

Удалятся не только контейнеры, но и тома, то есть все данные Postgres. При следующем старте база создастся заново и выполнит скрипты из `db/`. Операция необратима.

</details>

**4. Почему API обращается к базе по имени `db`?**

<details>
<summary>Показать ответ</summary>

Внутри сети Compose сервисы видны по именам — Docker резолвит их сам. IP-адреса контейнеров меняются при перезапуске, имя — нет.

</details>

**5. Вы добавили миграцию в `db/`, перезапустили — не применилась. Почему?**

<details>
<summary>Показать ответ</summary>

Скрипты из `docker-entrypoint-initdb.d` выполняются только при создании пустого тома. Варианты: накатить вручную через `psql`, пересоздать том с потерей данных или добавить в `ensure_schema()`.

</details>

**6. Зачем `healthcheck` у базы, если есть `depends_on`?**

<details>
<summary>Показать ответ</summary>

`depends_on` без условия ждёт только запуска контейнера, а не готовности Postgres принимать соединения. `condition: service_healthy` ждёт успешного `pg_isready`.

</details>

**7. Чем bind mount отличается от named volume?**

<details>
<summary>Показать ответ</summary>

Bind mount (`./web:/srv/web`) показывает папку хоста внутри контейнера — правки видны сразу. Named volume (`pgdata:`) — хранилище под управлением Docker, живущее независимо от контейнера.

</details>

**8. Что такое обратный прокси и зачем он здесь?**

<details>
<summary>Показать ответ</summary>

Сервер, принимающий запросы и переправляющий их дальше. nginx отдаёт статику быстрее Python и держит фронтенд с API на одном origin, благодаря чему не нужен CORS.

</details>

**9. Почему `--host 0.0.0.0` в команде uvicorn?**

<details>
<summary>Показать ответ</summary>

`127.0.0.1` внутри контейнера означает «только внутри этого контейнера». Снаружи, включая проброшенный порт, достучаться не выйдет.

</details>

**10. Сервер отдаёт новый код, а на экране старый интерфейс. Что делать?**

<details>
<summary>Показать ответ</summary>

Это кэш браузера: `Cmd/Ctrl + Shift + R`. Убедиться, что сервер действительно отдаёт новое, помогает `bash tools/check_deploy.sh` — он показывает содержимое контейнера и подключённые скрипты.

</details>

**11. Что заменить перед реальной эксплуатацией в первую очередь?**

<details>
<summary>Показать ответ</summary>

Пароли, код внутрь образа вместо монтирования, удаление демо-данных, HTTPS и аутентификацию. Без последней систему нельзя показывать наружу вообще.

</details>

Курс закончен. Порядок, в котором стоит закреплять материал руками:

1. Поднимите проект, откройте `/docs` и вызовите каждый эндпоинт.

5. Сломайте что-нибудь намеренно — остановите базу и посмотрите, как ведёт
   себя интерфейс и что покажет `/api/health`.

Последний пункт важнее первых четырёх. Понимание системы приходит не тогда,
когда она работает, а когда вы знаете, как именно она ломается.
