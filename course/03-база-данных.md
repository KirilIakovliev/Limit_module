# Лекция 3. База данных: PostgreSQL, SQL и индексы

## 3.1. Реляционная модель

База состоит из **таблиц**. Таблица — это строки (записи) и столбцы (поля).
Каждый столбец имеет тип: текст, число, дата, логическое значение.

```
companies
┌────┬──────────────────────┬────────────┬───────────┐
│ id │ name                 │ inn        │ group_id  │
├────┼──────────────────────┼────────────┼───────────┤
│  2 │ Магнитогорский МК    │ 7414003633 │         1 │
│  9 │ Северсталь           │ 3528000597 │         1 │
│  1 │ Магнит               │ 2309085638 │      NULL │
└────┴──────────────────────┴────────────┴───────────┘
```

**Первичный ключ** (`id`) — уникальный номер строки. По нему на строку
ссылаются.

**Внешний ключ** (`group_id`) — ссылка на строку другой таблицы. `NULL`
означает «ссылки нет» (Магнит не входит в группу). База следит, чтобы ссылка
вела на существующую строку: удалить группу, на которую ссылаются, просто так
не выйдет.

Так строятся связи:

- **один-ко-многим**: у одной компании много лимитов. Поэтому `company_id`
  лежит в таблице `limits`, а не список лимитов в `companies`.
- **многие-ко-многим**: если бы компания могла входить в несколько групп,
  понадобилась бы отдельная таблица связей.

## 3.2. Наши таблицы

```
companies ──┬── financial_indicators   показатели по годам
            ├── limits ── sublimits    лимиты и транши по ним
            ├── reserve_positions      резервы РСБУ/МСФО
            ├── limit_applications     заявки на рассмотрении
            ├── group_sublimits        сублимит внутри ГК
            └── company_groups         группа компаний (ссылка вверх)
```

Разбор `db/01_schema.sql`:

```sql
CREATE TABLE companies (
    id          BIGSERIAL PRIMARY KEY,
    name        TEXT        NOT NULL,
    inn         VARCHAR(12) NOT NULL UNIQUE,
    kpp         VARCHAR(9),
    industry    TEXT,
    is_active   BOOLEAN     NOT NULL DEFAULT TRUE,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

> **Где это в коде:** `db/01_schema.sql:9` — таблица `companies`;
> `db/01_schema.sql:42` — `financial_indicators`.

- `BIGSERIAL PRIMARY KEY` — автоматически растущее число, ключ строки
- `NOT NULL` — поле обязательно
- `UNIQUE` — двух компаний с одним ИНН быть не может; база это гарантирует,
  даже если приложение забудет проверить
- `DEFAULT TRUE` — значение по умолчанию
- `TIMESTAMPTZ` — время с часовым поясом. Всегда берите его, а не `TIMESTAMP`:
  иначе в проде вы однажды не поймёте, чьё это время
- `is_active` — вместо удаления строк помечаем их неактивными. Удалённая
  строка уносит с собой историю; помеченная остаётся для отчётов

### Показатели: длинная таблица вместо широкой

Можно было сделать столбцы `revenue_2021`, `revenue_2022`… Мы сделали иначе:

```sql
CREATE TABLE financial_indicators (
    company_id  BIGINT NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
    group_code  TEXT   NOT NULL CHECK (group_code IN ('balance','results','ratios')),
    ord         INT    NOT NULL,
    label       TEXT   NOT NULL,
    kind        TEXT   NOT NULL CHECK (kind IN ('money','pct','ratio')),
    year        INT    NOT NULL,
    value       NUMERIC(20,2)
);
```

Каждое число — отдельная строка: компания, группа, показатель, год, значение.
Появился 2025 год — просто добавляются строки, схема не меняется. Появился
новый показатель — то же самое. Это называется «длинный» (EAV-подобный) формат.

- `REFERENCES companies(id) ON DELETE CASCADE` — при удалении компании её
  показатели удалятся автоматически
- `CHECK (... IN (...))` — база не пропустит значение вне списка
- `NUMERIC(20,2)` — точное десятичное число, 2 знака после запятой.
  **Для денег никогда не используйте `float`**: 0.1 + 0.2 в нём даёт
  0.30000000000000004, и отчёты не сходятся на копейки

## 3.3. SQL: минимум, который нужен

### SELECT

```sql
SELECT name, inn          -- какие столбцы
FROM companies            -- откуда
WHERE is_active           -- условие отбора
ORDER BY name             -- сортировка
LIMIT 8;                  -- сколько строк вернуть
```

### JOIN — соединение таблиц

```sql
SELECT c.name, l.product, l.limit_amount
FROM companies c
JOIN limits l ON l.company_id = c.id
WHERE c.id = 2;
```

`c` и `l` — псевдонимы. `ON` описывает, как связать строки: берём строку
компании и все строки лимитов, где `company_id` равен её `id`.

`LEFT JOIN` отличается тем, что оставляет строку левой таблицы, даже если
справа совпадений нет — вместо них будет `NULL`. Мы используем его для группы:

```sql
FROM companies c
LEFT JOIN company_groups g ON g.id = c.group_id
```

Компания без группы всё равно попадёт в результат, `g.name` будет `NULL`.

### Агрегаты и GROUP BY

```sql
SELECT group_id,
       sum(sublimit_amount) AS amount,
       count(*)             AS members
FROM group_sublimits
GROUP BY group_id;
```

`GROUP BY` схлопывает строки в группы, агрегатные функции (`sum`, `count`,
`max`, `avg`) считают по каждой группе.

### CTE — временные таблицы внутри запроса

`WITH` позволяет назвать промежуточный результат и пользоваться им дальше.
Так написан весь наш генератор демо-данных:

```sql
WITH scale AS (
    SELECT id AS company_id, (0.2 + random() * 3.0) * 8000000 AS s
    FROM companies
),
raw AS (
    SELECT sc.company_id, y.year,
           round(sc.s * (0.82 + 0.09 * (y.year - 2021))::numeric, 2) AS revenue
    FROM scale sc CROSS JOIN generate_series(2021, 2024) AS y(year)
)
SELECT * FROM raw;
```

`generate_series(2021, 2024)` порождает четыре строки с годами. `CROSS JOIN`
даёт все сочетания: каждая компания × каждый год.

### LATERAL — «разворачивание» строки в несколько

Одна строка расчёта превращается в 22 строки показателей:

```sql
INSERT INTO financial_indicators (company_id, group_code, ord, label, kind, year, value)
SELECT c.company_id, v.group_code, v.ord, v.label, v.kind, c.year, v.value
FROM calc c
CROSS JOIN LATERAL (VALUES
    ('balance', 1, 'Активы, всего',       'money', c.assets),
    ('balance', 2, 'Внеоборотные активы', 'money', c.noncurrent_assets),
    ...
) AS v(group_code, ord, label, kind, value);
```

`LATERAL` значит «подзапрос видит столбцы внешнего запроса» — здесь `c.assets`.
Без него так не написать.

### Ловушка с random() внутри LATERAL

Мы на неё наступили: все пять продуктов компании получили одинаковую сумму.

```sql
-- было: random() вычисляется один раз на компанию
CROSS JOIN LATERAL (SELECT (1000000 + random() * 999000000) AS amt) AS a

-- стало: значение считается для каждой строки
WITH raw_limits AS (
    SELECT c.id, p.product, round((1000000 + random() * 999000000)::numeric, 2) AS amount
    FROM companies c CROSS JOIN LATERAL (VALUES ('Овердрафт'), ...) AS p(product)
)
INSERT INTO limits (...) SELECT ... FROM raw_limits;
```

Подзапрос, не зависящий от внешних столбцов, планировщик вправе вычислить
однократно. Урок: **если нужна случайность на строку — считайте её в списке
выборки, а не в некоррелированном подзапросе.**

### Типы и приведение

`random()` возвращает `double precision`, а `round(x, 2)` есть только для
`numeric`. Отсюда `::numeric` по всему коду — это оператор приведения типа.
Первый запуск нашего сида падал именно на этом.

### Демонстрация: random() внутри LATERAL

Задача: выдать каждому продукту компании свою случайную сумму.

```sql
CREATE TABLE demo_companies (id int, name text);
INSERT INTO demo_companies VALUES (1, 'Магнит'), (2, 'Северсталь');

SELECT c.name, p.product, round(a.amt) AS сумма
FROM demo_companies c
CROSS JOIN LATERAL (VALUES ('Овердрафт'), ('Гарантии'), ('Аккредитив')) AS p(product)
CROSS JOIN LATERAL (SELECT random() * 1000 AS amt) AS a;
```

```
    name    |  product   | сумма
------------+------------+-------
 Магнит     | Овердрафт  |   183
 Магнит     | Гарантии   |   183
 Магнит     | Аккредитив |   183
 Северсталь | Овердрафт  |   183
 Северсталь | Гарантии   |   183
 Северсталь | Аккредитив |   183
```

Одно значение на все шесть строк. План объясняет почему:

```
 Nested Loop
   ->  Seq Scan on demo_companies c
   ->  Materialize            ← результат посчитан один раз и переиспользован
         ->  Nested Loop
               ->  Result
```

**`Materialize`** — «вычислить и запомнить». Подзапрос
`(SELECT random() * 1000)` не ссылается ни на один внешний столбец, значит
с точки зрения планировщика его результат не может отличаться между строками.
Оптимизация законная — просто `random()` нарушает предположение, на котором
она построена.

**Починка 1 — считать в списке выборки:**

```sql
SELECT c.name, p.product, round(random() * 1000) AS сумма
FROM demo_companies c
CROSS JOIN LATERAL (VALUES ('Овердрафт'), ('Гарантии'), ('Аккредитив')) AS p(product);
```

```
 Магнит     | Овердрафт  |   284
 Магнит     | Гарантии   |   620      ← все значения разные
 Магнит     | Аккредитив |   769
 Северсталь | Овердрафт  |   814
```

**Починка 2 — сделать подзапрос зависимым от внешнего столбца:**

```sql
CROSS JOIN LATERAL (SELECT random() * 1000 + c.id * 0 AS amt) AS a
```

```
 Магнит     | Овердрафт  |   959
 Магнит     | Гарантии   |   959      ← пересчитан на каждую компанию,
 Магнит     | Аккредитив |   959         но один на её продукты
 Северсталь | Овердрафт  |    56
```

Разница между починками видна сразу: второй вариант даёт значение на
**компанию**, а не на строку, потому что зависит от `c.id`, а не от
`p.product`. Именно в такой форме баг и жил в проекте.

**Общий принцип.** SQL декларативен: вы описываете *что* получить, а *как* и
*сколько раз* считать — решает планировщик. Пока функции чистые (одинаковый
вход → одинаковый выход), это незаметно. `random()`, `now()`, `nextval()`
чистыми не являются, и с ними порядок вычислений становится виден.

## 3.4. Индексы — почему поиск быстрый

Без индекса база читает всю таблицу. Индекс — отдельная структура, по которой
можно найти нужные строки, не читая остальные.

### B-tree — обычный индекс

Сбалансированное дерево, поиск за `log(n)`. Подходит для `=`, `<`, `>`,
`BETWEEN`, `ORDER BY` и для `LIKE 'префикс%'` — но для последнего нужен
специальный класс операторов:

```sql
CREATE INDEX companies_search_prefix ON companies (search_name text_pattern_ops);
```

`text_pattern_ops` сравнивает строки побайтово (как C-локаль), а не по правилам
языка. Именно это позволяет использовать индекс для `LIKE 'маг%'`.

### GIN + pg_trgm — нечёткий поиск

```sql
CREATE EXTENSION pg_trgm;
CREATE INDEX companies_search_trgm ON companies USING gin (search_name gin_trgm_ops);
```

`pg_trgm` бьёт строку на триграммы (тройки символов): «магнит» → `маг`, `агн`,
`гни`, `нит`. GIN-индекс хранит, в каких строках какая триграмма встречается.
Это даёт поиск по подстроке в середине и устойчивость к опечаткам:

```sql
SELECT name, word_similarity('магнт', search_name) AS score
FROM companies
WHERE 'магнт' <% search_name
ORDER BY score DESC LIMIT 8;
```

`<%` — «похоже на слово внутри строки». Опечатка «магнт» находит «Магнит».

### Генерируемый столбец

Пользователь печатает «магн», а в базе «ООО Магнит» — префиксный поиск
не сработает. Решение:

```sql
ALTER TABLE companies ADD COLUMN search_name TEXT
GENERATED ALWAYS AS (
    lower(regexp_replace(name, '^(ООО|АО|ПАО|ЗАО|ГК|ИП|ОАО)\s+', ''))
) STORED;
```

> **Где это в коде:** `db/03_search_index.sql:11` — объявление колонки;
> `db/03_search_index.sql:19` — индекс `companies_search_prefix`;
> `api/app/main.py:34` — те же операции в списке `SEARCH_SCHEMA_SQL`, который
> выполняется при старте API.

`GENERATED ALWAYS AS ... STORED` — база сама пересчитывает столбец при каждой
вставке и изменении. Рассинхронизации быть не может в принципе.

## 3.5. Главный урок по производительности

Один и тот же запрос, один и тот же индекс, 200 000 строк:

```sql
-- 10,2 мс
SELECT ... WHERE search_name LIKE 'маг%' ORDER BY search_name LIMIT 8;

-- 0,08 мс
SELECT ... WHERE search_name LIKE 'маг%' ORDER BY search_name USING ~<~ LIMIT 8;
```

> **Где это в коде:** `api/app/main.py:137` — запрос `PREFIX_SQL` именно с
> `ORDER BY search_name USING ~<~`.

**Разница в 130 раз.** Причина: `text_pattern_ops` хранит значения в порядке
C-локали. Обычный `ORDER BY search_name` требует порядка по правилам русского
языка — это другой порядок, поэтому база вынуждена прочитать все 6 666
совпадений и отсортировать их. `USING ~<~` просит сортировку тем же
оператором, что в индексе: база идёт по индексу и останавливается на восьмой
строке.

Как это увидеть самому:

```sql
EXPLAIN ANALYZE
SELECT id, name FROM companies
WHERE search_name LIKE 'маг%' ORDER BY search_name USING ~<~ LIMIT 8;
```

В плане ищите:
- `Index Scan` — хорошо, идём по индексу
- `Seq Scan` — читаем всю таблицу, индекс не подошёл
- `Sort` / `Sort Method` — **сортировка есть, значит порядок не совпал с индексом**
- `actual time=...` — реальное время

Правило: увидели `Sort` там, где ждали `LIMIT` — разбирайтесь с сортировкой.

### Демонстрация: почему один и тот же запрос быстрее в 270 раз

Таблица `companies_big` — 200 000 компаний, два индекса: btree
(`text_pattern_ops`) и GIN (`gin_trgm_ops`). Запрашиваем 8 компаний на «маг».

**Вариант 1 — обычная сортировка:**

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, name FROM companies_big
WHERE search_name LIKE 'маг%' ORDER BY search_name LIMIT 8;
```

```
 Limit (actual time=11.896..11.898 rows=8 loops=1)
   ->  Sort (actual time=11.895..11.896 rows=8 loops=1)
         Sort Key: search_name
         Sort Method: top-N heapsort  Memory: 26kB
         ->  Bitmap Heap Scan on companies_big (actual time=2.451..8.073 rows=16667 loops=1)
               Recheck Cond: (search_name ~~ 'маг%'::text)
               Heap Blocks: exact=2532
               ->  Bitmap Index Scan on cb_trgm (actual time=2.095..2.095 rows=16667 loops=1)
 Execution Time: 11.992 ms
```

**Вариант 2 — сортировка оператором индекса:**

```sql
EXPLAIN (ANALYZE, COSTS OFF)
SELECT id, name FROM companies_big
WHERE search_name LIKE 'маг%' ORDER BY search_name USING ~<~ LIMIT 8;
```

```
 Limit (actual time=0.031..0.035 rows=8 loops=1)
   ->  Index Scan using cb_prefix on companies_big (actual time=0.030..0.034 rows=8 loops=1)
         Index Cond: ((search_name ~>=~ 'маг'::text) AND (search_name ~<~ 'мад'::text))
 Execution Time: 0.044 ms
```

**Разбор плана снизу вверх** — читать планы нужно именно так, от самых
вложенных строк к верхним.

Вариант 1:

| Строка плана | Что происходит |
|---|---|
| `Bitmap Index Scan on cb_trgm` | по триграммному индексу нашлись **16 667** строк |
| `Bitmap Heap Scan`, `Heap Blocks: exact=2532` | ради них прочитано 2 532 страницы с диска |
| `Sort`, `Sort Method: top-N heapsort` | все 16 667 отсортированы, чтобы выбрать 8 |
| `Execution Time: 11.992 ms` | итог |

Вариант 2:

| Строка плана | Что происходит |
|---|---|
| `Index Scan using cb_prefix` | идём по btree в порядке индекса |
| `Index Cond: search_name ~>=~ 'маг' AND ~<~ 'мад'` | префикс превращён в диапазон: от «маг» до «мад» |
| строки `Sort` нет | сортировать нечего, индекс уже в нужном порядке |
| `actual rows=8` | прочитано ровно 8 строк вместо 16 667 |

**Почему `USING ~<~` вообще что-то меняет.** Индекс с `text_pattern_ops`
хранит значения в порядке побайтового сравнения (C-локаль). Обычный
`ORDER BY search_name` требует порядка по правилам русского языка — это
**другой** порядок, поэтому индексный порядок не годится и нужна сортировка.
`USING ~<~` явно просит тот же оператор сравнения, что и в индексе, — и база
может просто идти по нему подряд.

**Как заметить это у себя:** если в плане есть `Sort` при наличии `LIMIT` —
база читает всё, чтобы отдать несколько строк. Почти всегда это лечится
согласованием `ORDER BY` с индексом.

## 3.7. Миграции

Схема живёт не в голове, а в файлах `db/`. Правило: **новое изменение — новый
файл**, старые не переписываются. Так историю можно воспроизвести с нуля.

Все наши миграции **идемпотентны** — повторный запуск ничего не ломает:

```sql
ALTER TABLE companies ADD COLUMN IF NOT EXISTS ogrn VARCHAR(15);
CREATE INDEX IF NOT EXISTS companies_search_prefix ON companies (...);
INSERT INTO company_groups (name) VALUES ('ГК «Северная сталь»')
ON CONFLICT (name) DO NOTHING;
UPDATE companies SET ogrn = COALESCE(ogrn, '1' || lpad(...));
```

`COALESCE(a, b)` возвращает `a`, если оно не `NULL`, иначе `b` — значение
проставляется только там, где его ещё нет.

Именно идемпотентность позволяет применять миграции при каждом старте API
(лекция 5) и не вести журнал «что накатано».

### Демонстрация: идемпотентность миграции

**Как ломается обычная миграция.** Файл выполнен три раза подряд:

```sql
CREATE TABLE IF NOT EXISTS demo_bad (id serial PRIMARY KEY, name text);
INSERT INTO demo_bad (name) VALUES ('ГК «Цветы»');
```

```
 id |    name
----+------------
  1 | ГК «Цветы»
  2 | ГК «Цветы»     ← дубль
  3 | ГК «Цветы»     ← ещё дубль
```

А добавление колонки со второго раза просто падает:

```sql
ALTER TABLE demo_companies ADD COLUMN kpp text;
```

```
ALTER TABLE                                             ← первый запуск
ERROR: column "kpp" of relation "demo_companies" already exists   ← второй
```

**Те же операции в идемпотентном виде:**

```sql
CREATE TABLE IF NOT EXISTS demo_groups (id serial PRIMARY KEY, name text UNIQUE);
ALTER TABLE demo_companies ADD COLUMN IF NOT EXISTS ogrn text;
INSERT INTO demo_groups (name) VALUES ('ГК «Цветы»') ON CONFLICT (name) DO NOTHING;
UPDATE demo_companies SET ogrn = COALESCE(ogrn, '1' || lpad(id::text, 12, '0'));
```

Три запуска подряд:

```
--- запуск 1: 1 строк в demo_groups
--- запуск 2: 1 строк в demo_groups
--- запуск 3: 1 строк в demo_groups

 id |    name    |     ogrn
----+------------+---------------
  1 | Магнит     | 1000000000001
  2 | Северсталь | 1000000000002
```

**Что делает каждая конструкция:**

| Конструкция | Поведение при повторе |
|---|---|
| `CREATE TABLE IF NOT EXISTS` | таблица есть — пропустить |
| `ADD COLUMN IF NOT EXISTS` | колонка есть — пропустить |
| `ON CONFLICT (name) DO NOTHING` | такая запись есть — не вставлять |
| `COALESCE(ogrn, ...)` | значение уже стоит — не перезаписывать |

**Зачем нам это было нужно.** Обычно применение миграций отслеживают: ведут
таблицу «какие файлы накатаны» и инструмент вроде Alembic. Раз наши миграции
безвредны при повторе, учёт не нужен вовсе — они выполняются **при каждом
старте API** (`api/app/main.py:55`, функция `ensure_schema`).

Это решило конкретную проблему: файлы из `db/` Postgres выполняет только при
создании пустого тома. База уже работала, `03_search_index.sql` молча
игнорировался, приложение падало с `column "search_name" does not exist`.
Теперь достаточно перезапустить API.

**Цена подхода:** миграции должны оставаться дешёвыми, потому что выполняются
на каждом старте. `CREATE INDEX` на большой таблице так запускать нельзя —
для таких случаев нужен нормальный инструмент миграций.

### Ловушка Docker, стоившая нам вечера

Файлы из `db/` Postgres выполняет **только при инициализации пустого тома**.
База уже работала — файл `03_search_index.sql` не применился, а код уже ждал
колонку `search_name`. Результат: `column "search_name" does not exist`.

Вывод: **инициализационные скрипты — не механизм миграций.** Они работают
один раз в жизни тома. Для работающей базы нужен свой запуск — у нас это
`ensure_schema()` при старте API.

## Проверьте себя
Ответы скрыты — сначала попробуйте сформулировать свой.

**1. Почему для денег нельзя использовать `float`?**

<details>
<summary>Показать ответ</summary>

Двоичная дробь не представляет 0,1 точно: 0.1 + 0.2 даёт 0.30000000000000004. На больших суммах отчёты разойдутся на копейки. Нужен `NUMERIC` — точная десятичная арифметика.

</details>

**2. Чем `JOIN` отличается от `LEFT JOIN`?**

<details>
<summary>Показать ответ</summary>

`JOIN` оставляет только строки, для которых есть совпадение справа. `LEFT JOIN` сохраняет строку левой таблицы в любом случае, подставляя `NULL`. Компания без группы попадёт в результат только со вторым.

</details>

**3. Что означает `Sort Method` в плане запроса?**

<details>
<summary>Показать ответ</summary>

База не смогла взять порядок из индекса и сортирует результат сама. При `LIMIT 8` это значит, что она прочитала все совпадения (у нас 6 666) ради восьми строк — отсюда 10 мс вместо 0,08 мс.

</details>

**4. Зачем `GENERATED ALWAYS AS ... STORED`, если то же можно посчитать в коде?**

<details>
<summary>Показать ответ</summary>

База пересчитывает колонку сама при любой вставке и изменении, включая ручные правки через psql. Рассинхронизации быть не может в принципе, а по такой колонке можно построить индекс.

</details>

**5. Почему файлы из `db/` не применились к работающей базе?**

<details>
<summary>Показать ответ</summary>

Postgres выполняет `/docker-entrypoint-initdb.d` только при инициализации пустого тома. Том уже существовал — скрипты пропущены молча. Поэтому миграции продублированы в `ensure_schema()` при старте API.

</details>

**6. Что такое идемпотентность миграции и зачем она?**

<details>
<summary>Показать ответ</summary>

Возможность применить файл повторно без вреда: `ADD COLUMN IF NOT EXISTS`, `ON CONFLICT DO NOTHING`, `COALESCE`. Позволяет выполнять миграции при каждом запуске и не вести учёт «что накатано».

</details>

**7. Почему `random()` внутри `CROSS JOIN LATERAL` дал всем продуктам одинаковую сумму?**

<details>
<summary>Показать ответ</summary>

Подзапрос не ссылался на столбцы внешнего запроса, поэтому планировщик вычислил его один раз на компанию. Случайность нужно считать в списке выборки или в CTE, зависящем от строки.

</details>

**8. Зачем `is_active` вместо удаления строки?**

<details>
<summary>Показать ответ</summary>

Удалённая строка уносит историю: отчёты за прошлые периоды перестают сходиться, ссылки на неё ломаются. Пометка сохраняет данные и убирает компанию из выдачи.

</details>

**9. Что делает `pg_trgm` и когда он нужен?**

<details>
<summary>Показать ответ</summary>

Разбивает строку на тройки символов и индексирует их. Даёт поиск по подстроке в середине и устойчивость к опечаткам: «магнт» находит «Магнит». Дороже префиксного поиска (64 мс против 0,08), поэтому у нас он запасной путь.

</details>

**10. Сколько запросов в секунду выдержала база на одном ядре и хватит ли этого на 100 человек?**

<details>
<summary>Показать ответ</summary>

7 493 запроса подсказок в секунду при 100 одновременных клиентах. Сто печатающих людей дают 200–300 запросов в секунду — запас примерно в 25 раз, ещё до использования остальных ядер.

</details>
