# Поиск подсказок: Postgres напрямую, без Redis

Документ отвечает на три вопроса: почему снимок справочника в Redis — плохая
идея, как должен работать выпадающий список, и выдержит ли это 100 пользователей
на машине 6 ядер / 10 ГБ.

---

## 1. Замеры

Всё измерено на **одном ядре и 3 ГБ RAM** — это слабее вашей машины, так что
на 6 ядрах цифры будут лучше. Таблица: 200 000 компаний, Postgres 16.

### Подсказки в поиске

| Запрос | Время | Что происходит |
|---|---|---|
| `LIKE 'маг%'` + `ORDER BY name LIMIT 8` | **10,2 мс** | нашёл 6 666 строк, отсортировал, отдал 8 |
| `LIKE 'маг%'` + `ORDER BY ... USING ~<~ LIMIT 8` | **0,08 мс** | идёт по индексу в нужном порядке, останавливается на 8-й строке |
| `ILIKE '%маг%'` (триграммы) | 16,1 мс | совпадение в середине названия |
| `word_similarity` (опечатка «магнт») | 64,0 мс | нечёткий поиск |
| ИНН `LIKE '7414%'` | 0,11 мс | btree по префиксу |

Разница между первой и второй строкой — в 130 раз, и это **одна и та же выборка
с одним и тем же индексом**. Дело только в сортировке: `text_pattern_ops`
хранит значения в порядке C-локали, и если `ORDER BY` этому порядку не
соответствует, Postgres вынужден вычитать все 6 666 совпадений и отсортировать
их, вместо того чтобы взять первые 8 прямо из индекса.

### Нагрузка (pgbench, одно ядро)

| Сценарий | Клиентов | TPS | Средняя задержка |
|---|---|---|---|
| Подсказки | 20 | 8 091 | 2,2 мс |
| Подсказки | 100 | 7 493 | 13,3 мс |
| Полный цикл «нажали Поиск» (5 запросов) | 100 | 2 085 | 48,0 мс |

### Снимок справочника в Redis, те же 200 000 компаний

| Операция | Время |
|---|---|
| Размер снимка | 25,2 МБ |
| Сериализация в JSON | 574 мс |
| Разбор JSON в процессе API | 459 мс |
| Поиск по списку, совпадение найдено рано | 0,10 мс |
| Поиск по списку, совпадений нет | **45,2 мс** |

## 2. Почему Redis здесь проигрывает

Вы правы, и формулировка в прошлом руководстве была плохая: решение, которое
«нормально до 20 000 записей», — это не решение, а отложенная переделка.

Разбор по пунктам:

**Поиск по списку — линейный.** Postgres по индексу делает `log(n)` шагов,
Python по списку — `n` сравнений. На 200 000 компаний запрос, который ничего не
находит (а пользователь постоянно печатает несуществующие сочетания, пока
набирает), стоит 45 мс против 0,08 мс у Postgres. Кэш оказывается **в 560 раз
медленнее** источника, который он должен был разгрузить.

**Снимок блокирует event loop.** 459 мс на разбор JSON — это не фон, это
остановка обработки всех запросов на полсекунды при каждом обновлении кэша.
На 100 пользователях это заметно.

**Данные устаревают.** Компанию завели в базе — в подсказках она появится через
час. Прямой запрос показывает её сразу.

**Больше движущихся частей.** Ещё один контейнер, ещё один режим отказа, ещё
одна вещь, которую нужно мониторить, — ради ускорения запроса, который и так
занимает 0,08 мс.

**Redis остаётся полезен**, но для другого: сессии, счётчики, блокировки,
результаты действительно тяжёлых агрегатов. Кэшировать индексированный
префиксный поиск смысла нет.

## 3. Ответ про 100 пользователей

Считаем сверху. Autocomplete с задержкой 160 мс: активно печатающий человек
даёт максимум 5–6 запросов в секунду, реально — 2–3. Сто человек **одновременно
печатающих** — это 200–300 запросов в секунду. Одно ядро выдало 7 493.

**Запас примерно в 25 раз, на одном ядре.** На шести — с большим избытком.

Полный цикл (нажали «Поиск» → четыре запроса) — 2 085 циклов в секунду. Если все
сто пользователей нажмут кнопку в одну и ту же секунду, это 100 циклов: около
5% мощности одного ядра.

Узким местом станет не Postgres, а:

- **Число соединений.** 100 пользователей ≠ 100 соединений к базе. Пул на
  10–20 соединений обслуживает эту нагрузку целиком, каждый запрос занимает
  соединение на 2 мс. Сейчас в `main.py` стоит `max_size=10` — этого хватает.
- **Один процесс uvicorn.** Python однопоточный; при 6 ядрах имеет смысл
  `--workers 4`. Тогда потолок вырастет ещё вчетверо.
- **Память.** Postgres на 10 ГБ: `shared_buffers` 2 ГБ, `work_mem` 16 МБ.
  Справочник на 200 000 компаний с индексами занимает 47 МБ — целиком
  помещается в кэш страниц и после первого прогрева читается из памяти.

Вывод: **прямые запросы в Postgres**. Redis не нужен ни на текущем объёме, ни на
двухсоттысячном.

## 4. Как работает выпадающий список

Порядок обработки одного нажатия клавиши:

1. **Меньше 3 символов** — запроса нет вообще. Отсекает основную массу.
2. **Debounce 160 мс.** Пока человек печатает, запросы не уходят; летит только
   последний. «Магнитогорский» — это один запрос, а не четырнадцать.
3. **Гонка ответов.** У каждого запроса есть номер, ответ с устаревшим номером
   отбрасывается — иначе медленный ответ на «маг» перезапишет быстрый на «магнит».
4. **Префиксный запрос** — `search_name LIKE 'маг%'`, порядок из индекса,
   `LIMIT 8`. 0,08 мс.
5. **Если нашлось меньше 3 строк** — добавляется нечёткий запрос
   (`word_similarity`), он ловит опечатки и совпадения в середине названия.
   64 мс, но случается редко: только когда префикс почти ничего не дал.

Ключевая деталь — колонка `search_name`. В базе «ООО Магнит», человек печатает
«магн». Без нормализации префиксный поиск не найдёт ничего, поэтому колонка
генерируется автоматически:

```sql
ALTER TABLE companies ADD COLUMN search_name TEXT
GENERATED ALWAYS AS (
    lower(regexp_replace(name, '^(ООО|АО|ПАО|ЗАО|ГК|ИП|ОАО)\s+', ''))
) STORED;
```

`GENERATED ALWAYS ... STORED` означает, что Postgres пересчитывает её сам при
любой вставке и обновлении — синхронизировать вручную нечего.

## 5. Что нужно сделать

### 5.1 Миграция базы

Колонку `search_name` и два индекса добавляет `db/03_search_index.sql`: btree
`text_pattern_ops` для префикса и GIN `gin_trgm_ops` для нечёткого поиска.
Данные не теряются, пересоздавать базу не нужно.

Ловушка: файлы из `db/` Postgres выполняет **только при первом старте пустого
тома**. Если база уже работает, миграция не применится сама, и код упадёт с
`column "search_name" does not exist`. Поэтому те же операции продублированы в
`ensure_schema()` в `app/main.py` — они идемпотентны и выполняются при каждом
запуске API. Отдельно накатывать ничего не нужно, но при желании можно:

```bash
docker compose exec -T db psql -U abb -d abb < db/03_search_index.sql
```

Убедиться, что схема на месте: поле `search_schema` в `/api/health`.

### 5.2 Запросы в `api/app/main.py`

`SEARCH_SQL` заменяется тремя запросами:

```python
# 1. Основной путь. ORDER BY ... USING ~<~ совпадает с порядком индекса,
#    поэтому сортировки нет: скан останавливается на восьмой строке.
PREFIX_SQL = """
SELECT id, name, inn, kpp, industry, 1.0::float AS score
FROM companies
WHERE is_active AND search_name LIKE %(prefix)s
ORDER BY search_name USING ~<~
LIMIT %(limit)s
"""

INN_SQL = """
SELECT id, name, inn, kpp, industry, 1.0::float AS score
FROM companies
WHERE is_active AND inn LIKE %(prefix)s
ORDER BY inn
LIMIT %(limit)s
"""

# 2. Запасной путь: опечатки и совпадение в середине названия.
FUZZY_SQL = """
SELECT id, name, inn, kpp, industry,
       word_similarity(%(q)s, search_name)::float AS score
FROM companies
WHERE is_active AND %(q)s <%% search_name
ORDER BY score DESC, name
LIMIT %(limit)s
"""
```

Обработчик:

```python
@app.get("/api/companies")
def search_companies(q_: str = Query(..., alias="q", min_length=3), limit: int = 8):
    """Подсказки. Префиксный поиск, при нехватке результатов — нечёткий."""
    params = {"q": q_.lower(), "prefix": f"{q_.lower()}%", "limit": limit}

    rows = q(INN_SQL, params) if q_[:1].isdigit() else q(PREFIX_SQL, params)

    if len(rows) < 3:
        seen = {r["id"] for r in rows}
        for r in q(FUZZY_SQL, params):
            if r["id"] not in seen:
                rows.append(r)
        rows = rows[:limit]

    return clean(rows)
```

В psycopg знак процента в SQL удваивается (`<%%`), иначе он будет принят за
плейсхолдер.

### 5.3 «Последнее обновление» — из Postgres

Отметка берётся из `company_sync_log` — это время, когда справочник последний
раз синхронизировали с источником. Именно это и нужно показывать; время
обновления кэша было бы просто временем работы фонового цикла.

```python
@app.get("/api/meta")
def meta():
    """Когда справочник компаний обновлялся последний раз."""
    if (hit := cache.get("meta")) is not None:
        return hit

    rows = q("""
        SELECT (SELECT count(*) FROM companies WHERE is_active) AS count,
               (SELECT max(updated_at) FROM companies) AS updated_at,
               (SELECT max(finished_at) FROM company_sync_log WHERE status = 'ok') AS synced_at
    """)
    r = rows[0]
    stamp = r["synced_at"] or r["updated_at"]
    out = {
        "cache": cache.enabled,
        "directory": {
            "count": r["count"],
            "updated_at": stamp.isoformat() if stamp else None,
            "source": "postgres",
        },
    }
    cache.set("meta", out, ttl=60)
    return out
```

Фронтенд менять не нужно: форма ответа та же, чип «Последнее обновление 16:20»
работает как раньше.

### 5.4 Redis — обратно в опциональные

В `docker-compose.yml` сервису `cache` возвращается `profiles: ["full"]`, из
`api` убирается `depends_on: cache` и `DIRECTORY_REFRESH_SECONDS`, а `REDIS_URL`
по умолчанию пустой. Обычный запуск — два образа, `db` и `api`.

Модуль `app/directory.py` удаляется целиком.

### 5.5 Проверка

```bash
docker compose down && docker compose up --build
docker compose exec -T db psql -U abb -d abb < db/03_search_index.sql

curl -s "localhost:8000/api/companies?q=маг"     # префикс
curl -s "localhost:8000/api/companies?q=7414"    # ИНН
curl -s "localhost:8000/api/companies?q=магнт"   # опечатка -> Магнит
curl -s localhost:8000/api/meta
```

План запроса должен показывать `Index Scan` без строки `Sort`:

```bash
docker compose exec db psql -U abb -d abb -c \
"EXPLAIN ANALYZE SELECT id, name FROM companies
 WHERE search_name LIKE 'маг%' ORDER BY search_name USING ~<~ LIMIT 8;"
```

Появилась строка `Sort Method` — значит `ORDER BY` не совпал с индексом, и вы
получите те самые 10 мс вместо 0,08 мс.

## 6. Когда всё-таки понадобится Redis

Не «когда компаний станет много» — Postgres с индексом это тянет. А когда
появится что-то из списка:

- **Тяжёлые агрегаты.** Сводка по всему портфелю лимитов, которая считается
  секунды и одинакова для всех, — вот её кэшировать стоит.
- **Сессии и права**, если модуль будет проверять доступ на каждый запрос.
- **Ограничение частоты запросов** — счётчики в Redis для этого созданы.
- **Несколько экземпляров API**, которым нужно общее состояние.

До тех пор одна база и один API-процесс проще, быстрее и надёжнее.
