Чему учит проект помимо кода

Пять сквозных идей, которые повторяются во всех лекциях:

Замеряйте, не угадывайте. Кэш в Redis оказался в 560 раз медленнее базы. Одна строчка ORDER BY ... USING ~<~ ускорила поиск в 130 раз. Ни то, ни другое нельзя было предсказать, глядя на код.

Один источник истины. Данные живут в Postgres. «Единый сублимит» не хранится, а считается суммой лимитов — иначе он однажды разойдётся со слагаемыми.

Идемпотентность. Миграция, которую можно применить дважды без вреда, позволяет применять её при каждом старте и не вести учёт «что накатано».

Ошибки должны быть видимыми. Тихий откат на демо-данные привёл к тому, что выдуманные цифры принимались за настоящие. Появился жёлтый значок.

Отложенное действие нужно уметь отменить. Таймер скрытия панели прятал её сразу после показа, если API отвечал быстрее 350 мс.

Лекция 1. Архитектура и стек

1.1. Что мы вообще построили

Лимитный модуль АББ — это веб-приложение: программа, которая живёт на сервере, а пользователь работает с ней через браузер. У неё три слоя, и это самая важная схема во всём курсе:

┌───────────────────────┐
│  БРАУЗЕР (клиент)     │   HTML + CSS + JavaScript
│  рисует интерфейс     │   сам ничего не хранит
└───────────┬───────────┘
            │ HTTP-запросы: GET /api/companies?q=маг
            ▼
┌───────────────────────┐
│  API (сервер)         │   Python + FastAPI
│  бизнес-логика        │   решает, что можно отдать и в каком виде
└───────────┬───────────┘
            │ SQL-запросы: SELECT ... FROM companies WHERE ...
            ▼
┌───────────────────────┐
│  БАЗА ДАННЫХ          │   PostgreSQL
│  хранит всё           │   единственный источник истины
└───────────────────────┘

Читать её нужно так: браузер ничего не знает о базе, а база ничего не знает о браузере. Между ними стоит API — переводчик. Браузер говорит на HTTP, база — на SQL, API умеет и то, и другое.

Зачем такое разделение? Три причины:

  1. Безопасность. Если бы браузер ходил в базу напрямую, пароль от базы лежал бы в JavaScript, который каждый может открыть через «Просмотр кода страницы».
  2. Контроль. API решает, что показывать. Браузер просит «данные компании 5» — API проверяет, можно ли, и отдаёт только разрешённые поля.
  3. Заменяемость. Захотите мобильное приложение — оно обратится к тому же API. Захотите сменить Postgres на что-то другое — браузер этого даже не заметит.

1.2. Ключевые определения

Без этих слов дальше будет непонятно.

HTTP — протокол, язык общения браузера и сервера. Запрос состоит из метода (GET — «дай», POST — «прими»), адреса (/api/companies) и, иногда, тела. Ответ — из кода состояния (200 — успех, 404 — не найдено, 500 — сервер сломался) и тела.

URL — адрес: http://localhost:8000/api/companies?q=маг&limit=8 - http — протокол - localhost — хост (эта же машина) - 8000 — порт (номер «двери» на машине; на одной машине много программ, порт говорит, к какой именно стучимся) - /api/companies — путь - ?q=маг&limit=8 — query string, параметры запроса

JSON — текстовый формат обмена данными. Выглядит как объект JavaScript:

{"id": 2, "name": "Магнитогорский МК", "inn": "7414003633"}

API отдаёт JSON, браузер его разбирает и рисует. Именно поэтому в проекте нет ни одной серверной HTML-страницы: сервер отдаёт данные, а разметку строит браузер.

REST — стиль проектирования API, где адрес обозначает ресурс, а метод — действие над ним. У нас честный REST:

GET /api/companies?q=маг            найти компании
GET /api/companies/2                карточка компании 2
GET /api/companies/2/limits         лимиты компании 2
GET /api/companies/2/reserves       резервы компании 2

SQL — язык запросов к реляционной базе. SELECT name FROM companies WHERE id = 2.

Контейнер — изолированная коробка с программой и всем, что ей нужно для работы. Разбирается в лекции 6.

Стек — это набор технологий. Наш:

Почему чистый JavaScript, а не React

React, Vue, Angular — популярные библиотеки. Мы их не взяли сознательно:

  • Сборка. React требует Node.js, npm, сборщика (Vite/Webpack). Это ещё один слой, который надо ставить, обновлять и чинить. У нас правка в styles.css сразу видна после F5.
  • Размер. React + ReactDOM — около 140 КБ. Весь наш фронтенд меньше.
  • Обучение. Вы просили научить, как всё устроено. React прячет работу с DOM за абстракциями; здесь вы видите каждый appendChild.

Обратная сторона честная: при росте проекта ручное управление состоянием станет утомительным. Признак, что пора переходить: когда одно изменение требует править состояние в трёх местах и вы начинаете забывать, в каких.

Почему отказались от кэша в Redis

Это хороший пример того, как решения принимаются по замерам, а не по привычке. Мы собирались держать справочник компаний в Redis и обновлять раз в час. Замерили на 200 000 компаний:

Операция Postgres Снимок в Redis
Префиксный поиск, есть совпадения 0,08 мс 0,10 мс
Поиск без совпадений 0,08 мс 45 мс
Разбор снимка при обновлении — 459 мс

Кэш оказался в 560 раз медленнее базы в самом частом сценарии — пользователь печатает и половина префиксов ничего не находит. Причина: Postgres идёт по индексу за log(n) шагов, а перебор списка в памяти линеен. Redis остался в проекте как опциональный сервис, но поиск ходит прямо в базу.

Вывод, который стоит запомнить: кэш ускоряет только то, что медленно. Кэшировать индексированный запрос — значит заменить быстрое на медленное.

1.5. Путь одного запроса целиком

Проследим, что происходит, когда пользователь печатает «маг» в поиске. Это самый полезный маршрут для понимания всей системы.

Шаг 1. Браузер, search-bar.js (web/js/search-bar.js:19 — таймер debounce). Событие input на поле ввода. Меньше 3 символов — ничего не делаем. Есть 3 — ставим таймер на 160 мс (debounce, лекция 4), чтобы не слать запрос на каждую букву.

Шаг 2. Браузер, api.js (web/js/api.js:42 — сборка адреса). Таймер сработал:

fetch('/api/companies?q=%D0%BC%D0%B0%D0%B3&limit=8')

Обратите внимание: «маг» превратилось в %D0%BC%D0%B0%D0%B3. Это процентное кодирование — в адресе разрешены только ASCII-символы. Браузер делает это сам через encodeURIComponent.

Шаг 3. Сеть. Уходит HTTP-запрос на localhost:8000.

Шаг 4. Сервер, uvicorn. Разбирает HTTP и передаёт FastAPI.

Шаг 5. Сервер, FastAPI. По пути /api/companies находит функцию search_companies, вытаскивает из URL параметры, проверяет типы.

Шаг 6. Сервер, main.py. Функция выполняет SQL (api/app/main.py:167 — обработчик, api/app/main.py:137 — текст запроса):

SELECT id, name, inn, kpp, industry, 1.0::float AS score
FROM companies
WHERE is_active AND search_name LIKE 'маг%'
ORDER BY search_name USING ~<~
LIMIT 8

Шаг 7. База. Идёт по btree-индексу, находит первые 8 строк, возвращает. 0,08 мс на 200 000 записей.

Шаг 8. Сервер. Превращает строки в список словарей, FastAPI сериализует их в JSON и отдаёт с кодом 200.

Шаг 9. Браузер, api.js. await response.json() — JSON стал массивом объектов JavaScript.

Шаг 10. Браузер, search-bar.js (web/js/search-bar.js:18 — счётчик запросов, web/js/search-bar.js:79 — подсветка совпадения). Проверяет номер запроса (не устарел ли ответ), строит HTML подсказок, вставляет в DOM.

Шаг 11. Пользователь видит список. Прошло около 200 мс, из которых 160 — наш собственный debounce.

Все дальнейшие лекции — детализация этих одиннадцати шагов.

1.6. Как принимались решения

Несколько правил, которые стоят за проектом. Они важнее конкретного кода.

Источник истины один. Данные живут в Postgres. Всё остальное — представления. Как только появляется вторая копия данных, появляется и вопрос «какая из них правильная».

Считать, а не хранить. «Единый сублимит» по глоссарию — совокупность лимитов клиента. Мы его не храним отдельно, а считаем суммой. Хранили бы — рано или поздно сумма разошлась бы со слагаемыми.

Замерять, а не угадывать. История с Redis выше. Ещё пример: запрос подсказок ускорился в 130 раз (10,2 мс → 0,08 мс) от одной строчки ORDER BY ... USING ~<~. Без EXPLAIN ANALYZE это не найти.

Идемпотентность. Каждая миграция может быть выполнена повторно без вреда. ADD COLUMN IF NOT EXISTS, ON CONFLICT DO NOTHING. Это позволяет применять их при каждом старте API и не думать «а накатывали ли мы её».

Явные ошибки лучше тихих. Когда фронтенд не мог достучаться до бэкенда, он молча переключался на демо-данные — и пользователь принимал выдуманные цифры за настоящие. Добавили заметный жёлтый значок «демо-данные».

Проверьте себя

Ответы скрыты — сначала попробуйте сформулировать свой.

1. Почему браузер не может обратиться к Postgres напрямую?

Показать ответ

Технически СУБД говорит по своему протоколу, которого браузер не знает. Но главное — безопасность: пароль от базы оказался бы в JavaScript, доступном каждому через «Просмотр кода». Плюс исчез бы слой, решающий, какие данные кому показывать.

2. Что означает код 404 и чем отличается от 500?

Показать ответ

404 — «сервер работает, но такого ресурса нет»: ошибка на стороне запроса. 500 — «сервер сломался при обработке»: ошибка на стороне сервера. У нас 404 отдаётся, когда компания не найдена; 500 мы видели, когда код обращался к несуществующей колонке search_name.

3. Что такое порт и зачем в адресе localhost:8000 число 8000?

Показать ответ

На одной машине работает много программ. Порт — номер «двери», по которому операционная система понимает, какой программе адресован пакет. У нас 8000 — API, 5433 — Postgres (наружу), 8080 — nginx в профиле full.

4. Что такое REST и в чём его идея на нашем примере?

Показать ответ

Адрес обозначает ресурс, метод — действие. GET /api/companies/2/limits читается как «дай лимиты компании 2». Не нужно придумывать имена вроде getCompanyLimits — структура адреса сама описывает данные.

5. Почему кэш может замедлить систему?

Показать ответ

Кэш ускоряет только то, что медленно. Postgres с индексом отвечает за 0,08 мс за log(n) шагов, а перебор списка в памяти линеен — на 200 000 записей поиск без совпадений занял 45 мс. Кэш оказался в 560 раз медленнее источника.

Лекция 2. Интерфейс: HTML, CSS и приёмы вёрстки

2.1. HTML — скелет

HTML описывает структуру документа. Он состоит из тегов:

<div class="tab">Текст</div>
  • <div> — открывающий тег, </div> — закрывающий
  • class="tab" — атрибут; классы нужны, чтобы CSS и JS могли найти элемент
  • «Текст» — содержимое

Теги вкладываются друг в друга и образуют дерево — DOM (Document Object Model). Браузер строит это дерево из текста файла, а JavaScript потом его меняет.

Атрибуты, которыми мы пользуемся

  • id="searchInput" — уникальное имя. По нему JS находит элемент: document.getElementById('searchInput')
  • class="tab is-active" — классов может быть несколько через пробел
  • data-company-id="20" — собственный атрибут. Всё, что начинается с data-, разрешено придумывать самому; в JS читается как node.dataset.companyId
  • hidden — элемент не отображается
  • aria-* — подсказки для программ чтения с экрана

Разбор нашего index.html

<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Лимитный модуль АББ</title>
  <link rel="stylesheet" href="css/styles.css?v=20260827-1530">
</head>
<body>
  ...
  <script src="js/format.js?v=..."></script>
</body>
</html>

Построчно:

  • <!DOCTYPE html> — «это современный HTML». Без него браузер включает режим совместимости с 1990-ми и вёрстка едет.
  • lang="ru" — язык. Влияет на переносы слов и на голос синтезатора речи.
  • charset="utf-8" — кодировка. Без неё кириллица превращается в «Ð›Ð¸Ð¼Ð¸Ñ‚».
  • viewport — на телефоне не притворяться широким экраном. Без этой строки мобильная вёрстка не работает вообще.
  • <link rel="stylesheet"> — подключение CSS.
  • ?v=20260827-1530 — обход кэша. Браузер хранит копию файла и может показывать старую версию после правок. Меняется номер версии — меняется адрес — браузер вынужден скачать заново. Мы натыкались на это в проекте: интерфейс выглядел старым, хотя файлы были новыми.
  • <script> в конце <body> — чтобы к моменту выполнения скриптов элементы уже существовали в DOM.

Порядок подключения скриптов

<script src="js/format.js"></script>      <!-- 1. ни от кого не зависит -->
<script src="js/demo-data.js"></script>   <!-- 2. использует Format       -->
<script src="js/api.js"></script>         <!-- 3. использует DemoData     -->
...
<script src="js/app.js"></script>         <!-- последний: связывает всё   -->

Обычные (не-модульные) скрипты выполняются по порядку, и всё объявленное через const Format = ... попадает в глобальную область. Поэтому порядок важен: api.js не может идти раньше demo-data.js.

CSS состоит из правил:

.tab-value {          /* селектор: к чему применяем */
  font-size: 15px;    /* свойство: значение          */

}

Селекторы, которые встречаются в проекте

Запись Значение

Каскад и специфичность

Когда два правила спорят за одно свойство, побеждает более специфичное: id (100) > класс (10) > тег (1). При равной специфичности побеждает то, что ниже в файле.

Это не теория. В проекте был ровно такой баг: после переделки в файле остался старый блок правил, и он шёл ниже нового:

.tab-tree.branch-right .tab-branch::before{right:0}          /* новое */
...
.tab-tree.branch-right .tab-branch::before{left:calc(...)}   /* старое, ниже */

Специфичность одинаковая, поэтому победило старое — и черта-указатель рисовалась слева вместо права. Лечение: удалить мёртвые правила. Если что-то стилизовано «не так», ищите второе правило ниже по файлу.

Переменные CSS

:root {
  --navy: #123A63;
  --radius-pill: 999px;
}
.search-button { background: var(--navy); }

Где это в коде: web/css/styles.css:8 — блок :root с палитрой и радиусами; web/css/styles.css:27 — градиент активной вкладки --gradient-tab.

:root — корень документа. Переменные наследуются вниз по дереву, поэтому их можно переопределять локально:

.tab-tree { --marker-gutter: 76px; }
@media (max-width: 1340px) {
  .tab-tree { --marker-gutter: 64px; }   /* на узком экране другое значение */
}

Где это в коде: web/css/styles.css:214 — объявление .tab-tree{--marker-gutter:76px;--row-capacity:5}; web/css/styles.css:612 — медиазапрос @media (max-width:1340px), переопределяющий отступ в 64px; web/js/tab-tree.js:278 — функция cssPx, читающая значение; web/js/tab-tree.js:396 — её вызов внутри layoutBranch.

Цепочка целиком: значение объявлено в CSS → медиазапрос меняет его в зависимости от ширины окна → JS читает уже актуальное и считает по нему положение строк. Ни одного числа продублировано не было.

Именно так у нас работает адаптивность отступов: JS читает getComputedStyle(treeRoot).getPropertyValue('--marker-gutter') и получает то значение, которое действует на текущей ширине экрана. Одна настройка живёт в одном месте.

2.3. Блочная модель и размеры

Каждый элемент — прямоугольник из четырёх слоёв:

┌─ margin (внешний отступ) ──────────────┐
│ ┌─ border (рамка) ───────────────────┐ │
│ │ ┌─ padding (внутренний отступ) ──┐ │ │
│ │ │        content (содержимое)    │ │ │
│ │ └────────────────────────────────┘ │ │
│ └────────────────────────────────────┘ │
└────────────────────────────────────────┘

По умолчанию width задаёт только content, и рамка с отступами прибавляются сверху — считать неудобно. Первое правило в нашем файле это исправляет:

* { box-sizing: border-box; }

Теперь width: 200px — это вся ширина вместе с рамкой и padding.

2.4. Flexbox — раскладка в строку

Почти все ряды карточек у нас — flex-контейнеры.

.tab-row {
  display: flex;              /* дети выстраиваются в строку     */
  justify-content: center;    /* выравнивание по главной оси     */
  align-items: stretch;       /* по поперечной: тянуть по высоте */
  gap: 12px;                  /* промежуток между детьми         */
  flex-wrap: wrap;            /* переносить, если не помещаются  */
}

У детей главное свойство — flex, это сокращение трёх:

.tab { flex: 0 1 var(--tab-basis); }
/*          │ │ └ базовый размер                        */
/*          │ └── flex-shrink: можно ли сжимать (1 = да) */
/*          └──── flex-grow: можно ли растягивать (0 = нет) */

Как мы добились одинаковой ширины карточек

Сначала было flex: 1 1 0 — «разделите строку поровну». Проблема: строка из 4 карточек делила ширину на 4, строка из 5 — на 5, и карточки получались разного размера в разных рядах.

Решение — считать ширину от самого ёмкого ряда:

.tab-row {
  --tab-basis: calc((100% - (var(--row-capacity) - 1) * 12px) / var(--row-capacity));
}
.tab { flex: 0 1 var(--tab-basis); }

--row-capacity: 5 — «в самом длинном ряду 5 карточек». Формула: из ширины строки вычесть все промежутки и разделить на 5. Ряд из 3 карточек получает те же по ширине карточки, просто занимает 3/5 строки.

Проценты в calc внутри flex-basis

100% в --tab-basis считается от ширины родителя (строки) в момент применения. Это работает, потому что переменная объявлена на .tab-row, а используется у детей: подстановка текстовая, вычисление — в контексте ребёнка.

2.5. Grid — раскладка в таблицу

Структура ГК — это сетка из пяти равных колонок:

.group-grid {
  display: grid;
  grid-template-columns: repeat(5, minmax(0, 1fr));
  gap: 12px;
}
  • 1fr — «одна доля свободного места»; пять таких колонок равны между собой
  • minmax(0, 1fr) — важная деталь: без minmax(0, ...) колонка не может стать уже своего содержимого, и длинное слово ломает всю сетку

Каждый ряд компаний — отдельная сетка с теми же настройками, поэтому колонки всех рядов выстраиваются друг под другом.

2.6. Анимации: два приёма

Раскрытие уровня через grid-template-rows

Классическая беда: height нельзя плавно анимировать от нуля до «сколько получится», потому что height: auto не число. Обходной приём:

.tab-level {
  display: grid;
  grid-template-rows: 0fr;                /* закрыто */
  transition: grid-template-rows .48s;
}
.tab-level.is-open { grid-template-rows: 1fr; }   /* открыто */
.tab-level > * { overflow: hidden; min-height: 0; }

Где это в коде: web/css/styles.css:195 — правило .tab-level; web/css/styles.css:77 — тот же приём для заголовка страницы (.page-title-wrap), который схлопывается при переходе к результатам.

fr — доля. 0fr — нулевая высота, 1fr — вся нужная. Между ними браузер умеет анимировать. overflow: hidden на ребёнке обязателен, иначе содержимое вылезет за пределы схлопнутой строки.

Сдвиг строки через transform

.tab-row { transition: transform .55s cubic-bezier(.22,.7,.2,1); }

Почему transform: translateX(-56px), а не left: -56px? Потому что transform обрабатывается видеокартой и не заставляет браузер пересчитывать раскладку всей страницы. Правило: анимируйте transform и opacity, всё остальное — только когда иначе никак.

Где это в коде: web/css/styles.css:261 — .tab-row с transition: transform; сам сдвиг назначает web/js/tab-tree.js:385 (layoutBranch).

cubic-bezier(.22,.7,.2,1) — кривая скорости: быстрый старт, мягкое торможение. Движение выглядит естественнее, чем равномерное.

Пульсация стрелок

@keyframes arrowPulse {
  0%, 100% { opacity: .14; }
  50%      { opacity: .72; }
}
.row-arrow { animation: arrowPulse 3.4s ease-in-out infinite; }

Где это в коде: web/css/styles.css:224 — .row-arrow (позиция и анимация); web/css/styles.css:247 — сами кадры @keyframes arrowPulse; web/js/tab-tree.js:362 — placeArrows, расставляющая стрелки по краям карточек.

@keyframes описывает кадры в процентах от длительности. Синхронность двух стрелок обеспечивается тем, что анимация назначается им одновременно и с одинаковой задержкой: при возврате в центр класс снимается с обеих сразу, и отсчёт для обеих начинается заново.

2.7. Контекст наложения — самый коварный баг проекта

Симптом: выпадающий список подсказок оказывался под карточками результатов, хотя у него z-index: 30, а у карточек ничего.

Причина: свойство transform создаёт контекст наложения (stacking context). Внутри него z-index детей действует только относительно друг друга, а сам контекст соревнуется с соседями как единое целое.

.hero          (есть transform → свой контекст)
   └─ .suggestions  z-index: 30    ← 30 действует только внутри .hero
.result-panel  (есть transform → свой контекст)
   └─ карточки

Где это в коде: web/css/styles.css:66 — .hero с transform и z-index: 20; web/css/styles.css:161 — .result-panel с z-index: 1; web/css/styles.css:141 — .suggestions с z-index: 30.

Оба контекста имеют z-index: auto, значит порядок определяется положением в документе — .result-panel идёт ниже, поэтому рисуется поверх. Лечение — задать порядок самим контекстам:

.hero         { position: relative; z-index: 20; }
.result-panel { position: relative; z-index: 1; }

Запомните: transform, filter, opacity < 1, will-change создают контекст наложения. Если z-index «не работает» — ищите такого родителя.

2.8. Тени, рамки и геометрия

--shadow-tab: 2px 3px 6px rgba(18,58,99,.14),
              4px 8px 16px rgba(18,58,99,.16);

Формат: смещение-X смещение-Y размытие цвет. Можно перечислить несколько теней через запятую — ближняя даёт чёткость, дальняя мягкость. Тень автоматически повторяет border-radius элемента.

Отдельная ловушка, на которую мы наткнулись: у активной вкладки была border-color: transparent поверх горизонтального градиента. Прозрачная рамка пропускает фон насквозь, поэтому слева рамка выглядела тёмной, а справа светлой. Два лечения:

background-clip: padding-box;   /* фон не заходит под рамку */
border-color: #1B4E80;          /* явный цвет со всех сторон */

2.9. Размеры по содержимому: min-content и max-content

Это ключ к адаптивной ширине карточек.

  • max-content — ширина текста, если запретить переносы вообще
  • min-content — ширина самого длинного неразрывного слова

Для «Магнитогорский МК»: max-content ≈ 192px, min-content ≈ 165px («Магнитогорский»). Для ИНН 7414003633 они совпадают — в числе нет пробелов, разорвать его нельзя.

На этом построен двухступенчатый подбор ширины верхней строки (реализация в лекции 4): сначала пробуем max-content — весь текст в строку; не помещается — берём min-content, тогда название переносится по пробелам, но ни слово, ни число не рвутся.

Плюс страховка на крайний случай:

.tab-value { overflow-wrap: break-word; }

Разрешает разорвать слово, только если оно не помещается никак.

2.10. Медиазапросы

@media (max-width: 1340px) { .tab-tree { --marker-gutter: 64px; } }
@media (max-width: 1100px) { .tab-tree { --row-capacity: 3; } }
@media (max-width: 760px)  { .tab-tree { --row-capacity: 2; } }

Читается: «при ширине окна не больше 1340px применить эти правила». Мы меняем не размеры напрямую, а переменные — и вся раскладка, завязанная на них, перестраивается сама.

Ещё один важный запрос:

@media (prefers-reduced-motion: reduce) {
  * { animation-duration: .01ms !important; transition-duration: .01ms !important; }
}

Часть людей отключает анимации в системе — от них укачивает. Уважать эту настройку — норма.

2.11. Псевдоэлементы как инструмент

::before и ::after создают элемент, которого нет в HTML. Обязателен content, иначе не появится.

Черта-указатель раскрытого уровня:

.tab-branch::before {
  content: "";
  position: absolute; top: 10px;
  width: 56px; height: 2px;
  background: var(--blue-400);
  display: none;
}
.tab-tree.branch-left  .tab-branch::before { display: block; left: 0; }
.tab-tree.branch-right .tab-branch::before { display: block; right: 0; }

Разделители в блоке ИНН/КПП — тоже псевдоэлементы:

.tab-pair::before, .tab-pair::after {

  top: 24%; height: 52%; width: 1px;
  background: var(--line);
}
.tab-pair::before { left: 0; }

Где это в коде: web/css/styles.css:252 — черта уровня .tab-branch::before; web/css/styles.css:345 — блок .tab-pair с разделителями по краям.

Высота 52% и отступ сверху 24% дают короткую черту по центру — визуально это разделитель, а не рамка.

Лекция 3. База данных: PostgreSQL, SQL и индексы

3.1. Реляционная модель

База состоит из таблиц. Таблица — это строки (записи) и столбцы (поля). Каждый столбец имеет тип: текст, число, дата, логическое значение.

companies
┌────┬──────────────────────┬────────────┬───────────┐
│ id │ name                 │ inn        │ group_id  │
├────┼──────────────────────┼────────────┼───────────┤
│  2 │ Магнитогорский МК    │ 7414003633 │         1 │
│  9 │ Северсталь           │ 3528000597 │         1 │
│  1 │ Магнит               │ 2309085638 │      NULL │
└────┴──────────────────────┴────────────┴───────────┘

Первичный ключ (id) — уникальный номер строки. По нему на строку ссылаются.

Внешний ключ (group_id) — ссылка на строку другой таблицы. NULL означает «ссылки нет» (Магнит не входит в группу). База следит, чтобы ссылка вела на существующую строку: удалить группу, на которую ссылаются, просто так не выйдет.

Так строятся связи:

  • один-ко-многим: у одной компании много лимитов. Поэтому company_id лежит в таблице limits, а не список лимитов в companies.
  • многие-ко-многим: если бы компания могла входить в несколько групп, понадобилась бы отдельная таблица связей.

3.2. Наши таблицы

companies ──┬── financial_indicators   показатели по годам
            ├── limits ── sublimits    лимиты и транши по ним
            ├── reserve_positions      резервы РСБУ/МСФО
            ├── limit_applications     заявки на рассмотрении
            ├── group_sublimits        сублимит внутри ГК
            └── company_groups         группа компаний (ссылка вверх)

Разбор db/01_schema.sql:

CREATE TABLE companies (
    id          BIGSERIAL PRIMARY KEY,
    name        TEXT        NOT NULL,
    inn         VARCHAR(12) NOT NULL UNIQUE,
    kpp         VARCHAR(9),
    industry    TEXT,
    is_active   BOOLEAN     NOT NULL DEFAULT TRUE,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

Где это в коде: db/01_schema.sql:9 — таблица companies; db/01_schema.sql:42 — financial_indicators.

  • BIGSERIAL PRIMARY KEY — автоматически растущее число, ключ строки
  • NOT NULL — поле обязательно
  • UNIQUE — двух компаний с одним ИНН быть не может; база это гарантирует, даже если приложение забудет проверить
  • DEFAULT TRUE — значение по умолчанию
  • TIMESTAMPTZ — время с часовым поясом. Всегда берите его, а не TIMESTAMP: иначе в проде вы однажды не поймёте, чьё это время
  • is_active — вместо удаления строк помечаем их неактивными. Удалённая строка уносит с собой историю; помеченная остаётся для отчётов

Показатели: длинная таблица вместо широкой

Можно было сделать столбцы revenue_2021, revenue_2022… Мы сделали иначе:

CREATE TABLE financial_indicators (
    company_id  BIGINT NOT NULL REFERENCES companies(id) ON DELETE CASCADE,
    group_code  TEXT   NOT NULL CHECK (group_code IN ('balance','results','ratios')),
    ord         INT    NOT NULL,
    label       TEXT   NOT NULL,
    kind        TEXT   NOT NULL CHECK (kind IN ('money','pct','ratio')),
    year        INT    NOT NULL,
    value       NUMERIC(20,2)
);

Каждое число — отдельная строка: компания, группа, показатель, год, значение. Появился 2025 год — просто добавляются строки, схема не меняется. Появился новый показатель — то же самое. Это называется «длинный» (EAV-подобный) формат.

  • REFERENCES companies(id) ON DELETE CASCADE — при удалении компании её показатели удалятся автоматически
  • CHECK (... IN (...)) — база не пропустит значение вне списка
  • NUMERIC(20,2) — точное десятичное число, 2 знака после запятой. Для денег никогда не используйте float: 0.1 + 0.2 в нём даёт 0.30000000000000004, и отчёты не сходятся на копейки

3.3. SQL: минимум, который нужен

SELECT

SELECT name, inn          -- какие столбцы
FROM companies            -- откуда
WHERE is_active           -- условие отбора
ORDER BY name             -- сортировка
LIMIT 8;                  -- сколько строк вернуть

JOIN — соединение таблиц

SELECT c.name, l.product, l.limit_amount
FROM companies c
JOIN limits l ON l.company_id = c.id
WHERE c.id = 2;

c и l — псевдонимы. ON описывает, как связать строки: берём строку компании и все строки лимитов, где company_id равен её id.

LEFT JOIN отличается тем, что оставляет строку левой таблицы, даже если справа совпадений нет — вместо них будет NULL. Мы используем его для группы:

FROM companies c
LEFT JOIN company_groups g ON g.id = c.group_id

Компания без группы всё равно попадёт в результат, g.name будет NULL.

Агрегаты и GROUP BY

SELECT group_id,
       sum(sublimit_amount) AS amount,
       count(*)             AS members
FROM group_sublimits
GROUP BY group_id;

GROUP BY схлопывает строки в группы, агрегатные функции (sum, count, max, avg) считают по каждой группе.

CTE — временные таблицы внутри запроса

WITH позволяет назвать промежуточный результат и пользоваться им дальше. Так написан весь наш генератор демо-данных:

WITH scale AS (
    SELECT id AS company_id, (0.2 + random() * 3.0) * 8000000 AS s
    FROM companies
),
raw AS (
    SELECT sc.company_id, y.year,
           round(sc.s * (0.82 + 0.09 * (y.year - 2021))::numeric, 2) AS revenue
    FROM scale sc CROSS JOIN generate_series(2021, 2024) AS y(year)
)
SELECT * FROM raw;

generate_series(2021, 2024) порождает четыре строки с годами. CROSS JOIN даёт все сочетания: каждая компания × каждый год.

LATERAL — «разворачивание» строки в несколько

Одна строка расчёта превращается в 22 строки показателей:

INSERT INTO financial_indicators (company_id, group_code, ord, label, kind, year, value)
SELECT c.company_id, v.group_code, v.ord, v.label, v.kind, c.year, v.value
FROM calc c
CROSS JOIN LATERAL (VALUES
    ('balance', 1, 'Активы, всего',       'money', c.assets),
    ('balance', 2, 'Внеоборотные активы', 'money', c.noncurrent_assets),
    ...
) AS v(group_code, ord, label, kind, value);

LATERAL значит «подзапрос видит столбцы внешнего запроса» — здесь c.assets. Без него так не написать.

Ловушка с random() внутри LATERAL

Мы на неё наступили: все пять продуктов компании получили одинаковую сумму.

-- было: random() вычисляется один раз на компанию
CROSS JOIN LATERAL (SELECT (1000000 + random() * 999000000) AS amt) AS a

-- стало: значение считается для каждой строки
WITH raw_limits AS (
    SELECT c.id, p.product, round((1000000 + random() * 999000000)::numeric, 2) AS amount
    FROM companies c CROSS JOIN LATERAL (VALUES ('Овердрафт'), ...) AS p(product)
)
INSERT INTO limits (...) SELECT ... FROM raw_limits;

Подзапрос, не зависящий от внешних столбцов, планировщик вправе вычислить однократно. Урок: если нужна случайность на строку — считайте её в списке выборки, а не в некоррелированном подзапросе.

Типы и приведение

random() возвращает double precision, а round(x, 2) есть только для numeric. Отсюда ::numeric по всему коду — это оператор приведения типа. Первый запуск нашего сида падал именно на этом.

Демонстрация: random() внутри LATERAL

Задача: выдать каждому продукту компании свою случайную сумму.

CREATE TABLE demo_companies (id int, name text);
INSERT INTO demo_companies VALUES (1, 'Магнит'), (2, 'Северсталь');

SELECT c.name, p.product, round(a.amt) AS сумма
FROM demo_companies c
CROSS JOIN LATERAL (VALUES ('Овердрафт'), ('Гарантии'), ('Аккредитив')) AS p(product)
CROSS JOIN LATERAL (SELECT random() * 1000 AS amt) AS a;

    name    |  product   | сумма
------------+------------+-------
 Магнит     | Овердрафт  |   183
 Магнит     | Гарантии   |   183
 Магнит     | Аккредитив |   183
 Северсталь | Овердрафт  |   183
 Северсталь | Гарантии   |   183
 Северсталь | Аккредитив |   183

Одно значение на все шесть строк. План объясняет почему:

 Nested Loop
   ->  Seq Scan on demo_companies c
   ->  Materialize            ← результат посчитан один раз и переиспользован
         ->  Nested Loop
               ->  Result

Materialize — «вычислить и запомнить». Подзапрос (SELECT random() * 1000) не ссылается ни на один внешний столбец, значит с точки зрения планировщика его результат не может отличаться между строками. Оптимизация законная — просто random() нарушает предположение, на котором она построена.

Починка 1 — считать в списке выборки:

SELECT c.name, p.product, round(random() * 1000) AS сумма
FROM demo_companies c
CROSS JOIN LATERAL (VALUES ('Овердрафт'), ('Гарантии'), ('Аккредитив')) AS p(product);

 Магнит     | Овердрафт  |   284
 Магнит     | Гарантии   |   620      ← все значения разные
 Магнит     | Аккредитив |   769
 Северсталь | Овердрафт  |   814

Починка 2 — сделать подзапрос зависимым от внешнего столбца:

CROSS JOIN LATERAL (SELECT random() * 1000 + c.id * 0 AS amt) AS a

 Магнит     | Овердрафт  |   959
 Магнит     | Гарантии   |   959      ← пересчитан на каждую компанию,
 Магнит     | Аккредитив |   959         но один на её продукты
 Северсталь | Овердрафт  |    56

Разница между починками видна сразу: второй вариант даёт значение на компанию, а не на строку, потому что зависит от c.id, а не от p.product. Именно в такой форме баг и жил в проекте.

Общий принцип. SQL декларативен: вы описываете что получить, а как и сколько раз считать — решает планировщик. Пока функции чистые (одинаковый вход → одинаковый выход), это незаметно. random(), now(), nextval() чистыми не являются, и с ними порядок вычислений становится виден.

3.4. Индексы — почему поиск быстрый

Без индекса база читает всю таблицу. Индекс — отдельная структура, по которой можно найти нужные строки, не читая остальные.

B-tree — обычный индекс

Сбалансированное дерево, поиск за log(n). Подходит для =, <, >, BETWEEN, ORDER BY и для LIKE 'префикс%' — но для последнего нужен специальный класс операторов:

CREATE INDEX companies_search_prefix ON companies (search_name text_pattern_ops);

text_pattern_ops сравнивает строки побайтово (как C-локаль), а не по правилам языка. Именно это позволяет использовать индекс для LIKE 'маг%'.

GIN + pg_trgm — нечёткий поиск

CREATE EXTENSION pg_trgm;
CREATE INDEX companies_search_trgm ON companies USING gin (search_name gin_trgm_ops);

pg_trgm бьёт строку на триграммы (тройки символов): «магнит» → маг, агн, гни, нит. GIN-индекс хранит, в каких строках какая триграмма встречается. Это даёт поиск по подстроке в середине и устойчивость к опечаткам:

SELECT name, word_similarity('магнт', search_name) AS score
FROM companies
WHERE 'магнт' <% search_name
ORDER BY score DESC LIMIT 8;

<% — «похоже на слово внутри строки». Опечатка «магнт» находит «Магнит».

Генерируемый столбец

Пользователь печатает «магн», а в базе «ООО Магнит» — префиксный поиск не сработает. Решение:

ALTER TABLE companies ADD COLUMN search_name TEXT
GENERATED ALWAYS AS (
    lower(regexp_replace(name, '^(ООО|АО|ПАО|ЗАО|ГК|ИП|ОАО)\s+', ''))
) STORED;

Где это в коде: db/03_search_index.sql:11 — объявление колонки; db/03_search_index.sql:19 — индекс companies_search_prefix; api/app/main.py:34 — те же операции в списке SEARCH_SCHEMA_SQL, который выполняется при старте API.

GENERATED ALWAYS AS ... STORED — база сама пересчитывает столбец при каждой вставке и изменении. Рассинхронизации быть не может в принципе.

3.5. Главный урок по производительности

Один и тот же запрос, один и тот же индекс, 200 000 строк:

-- 10,2 мс
SELECT ... WHERE search_name LIKE 'маг%' ORDER BY search_name LIMIT 8;

-- 0,08 мс
SELECT ... WHERE search_name LIKE 'маг%' ORDER BY search_name USING ~<~ LIMIT 8;

Где это в коде: api/app/main.py:137 — запрос PREFIX_SQL именно с ORDER BY search_name USING ~<~.

Разница в 130 раз. Причина: text_pattern_ops хранит значения в порядке C-локали. Обычный ORDER BY search_name требует порядка по правилам русского языка — это другой порядок, поэтому база вынуждена прочитать все 6 666 совпадений и отсортировать их. USING ~<~ просит сортировку тем же оператором, что в индексе: база идёт по индексу и останавливается на восьмой строке.

Как это увидеть самому:

EXPLAIN ANALYZE
SELECT id, name FROM companies
WHERE search_name LIKE 'маг%' ORDER BY search_name USING ~<~ LIMIT 8;

В плане ищите: - Index Scan — хорошо, идём по индексу - Seq Scan — читаем всю таблицу, индекс не подошёл - Sort / Sort Method — сортировка есть, значит порядок не совпал с индексом - actual time=... — реальное время

Правило: увидели Sort там, где ждали LIMIT — разбирайтесь с сортировкой.

Демонстрация: почему один и тот же запрос быстрее в 270 раз

Таблица companies_big — 200 000 компаний, два индекса: btree (text_pattern_ops) и GIN (gin_trgm_ops). Запрашиваем 8 компаний на «маг».

Вариант 1 — обычная сортировка:

Разбор плана снизу вверх — читать планы нужно именно так, от самых вложенных строк к верхним.

Вариант 1:

Строка плана Что происходит

Почему USING ~<~ вообще что-то меняет. Индекс с text_pattern_ops хранит значения в порядке побайтового сравнения (C-локаль). Обычный ORDER BY search_name требует порядка по правилам русского языка — это другой порядок, поэтому индексный порядок не годится и нужна сортировка. USING ~<~ явно просит тот же оператор сравнения, что и в индексе, — и база может просто идти по нему подряд.

Как заметить это у себя: если в плане есть Sort при наличии LIMIT — база читает всё, чтобы отдать несколько строк. Почти всегда это лечится согласованием ORDER BY с индексом.

3.7. Миграции

Схема живёт не в голове, а в файлах db/. Правило: новое изменение — новый файл, старые не переписываются. Так историю можно воспроизвести с нуля.

Все наши миграции идемпотентны — повторный запуск ничего не ломает:

ALTER TABLE companies ADD COLUMN IF NOT EXISTS ogrn VARCHAR(15);
CREATE INDEX IF NOT EXISTS companies_search_prefix ON companies (...);
INSERT INTO company_groups (name) VALUES ('ГК «Северная сталь»')
ON CONFLICT (name) DO NOTHING;
UPDATE companies SET ogrn = COALESCE(ogrn, '1' || lpad(...));

COALESCE(a, b) возвращает a, если оно не NULL, иначе b — значение проставляется только там, где его ещё нет.

Именно идемпотентность позволяет применять миграции при каждом старте API (лекция 5) и не вести журнал «что накатано».

Демонстрация: идемпотентность миграции

Как ломается обычная миграция. Файл выполнен три раза подряд:

  2 | ГК «Цветы»     ← дубль

  • compact выбирает единицу по величине: миллиарды с двумя знаками, миллионы с одним. На карточке «1,88 млрд ₽» читается мгновенно, а «1 880 000 000 ₽» требует пересчёта в уме.
  • delta возвращает знак − (U+2212, минус), а не дефис: типографски это разные символы, и минус выравнивается по ширине с плюсом.

5.4. Подключение к базе

from psycopg_pool import ConnectionPool
from psycopg.rows import dict_row

db_pool = ConnectionPool(DATABASE_DSN, min_size=1, max_size=10,
                         open=False, kwargs={"row_factory": dict_row})

Где это в коде: api/app/main.py:20 — создание пула; api/app/main.py:115 — функция db_query.

Пул соединений. Установка соединения с Postgres стоит миллисекунды и ресурсы. Пул держит их наготове и выдаёт по требованию. max_size=10 — десяти соединений хватает на сотню пользователей: каждый запрос держит соединение 2 мс, остальное время оно свободно.

row_factory=dict_row — возвращать строки словарями (row["name"]), а не кортежами (row[1]). Код становится читаемым.

def db_query(sql: str, params: tuple = ()) -> list[dict]:
    with db_pool.connection() as conn, conn.cursor() as cur:
        cur.execute(sql, params)
        return cur.fetchall()

with — контекстный менеджер: соединение возвращается в пул автоматически, даже если внутри произошла ошибка. Без него утечка соединений — вопрос времени.

SQL-инъекции

Никогда не склеивайте SQL из строк:

cur.execute(f"SELECT * FROM companies WHERE inn = '{user_input}'")   # ОПАСНО

Если ввести ' OR '1'='1, условие станет всегда истинным. Правильно:

cur.execute("SELECT * FROM companies WHERE inn = %s", (user_input,))

Драйвер передаёт значение отдельно от текста запроса, и оно не может стать частью команды. У нас так везде — обратите внимание на именованные параметры:

db_query(PREFIX_SQL, {"q": query.lower(), "prefix": f"{query.lower()}%", "limit": limit})

В SQL они выглядят как %(prefix)s. И отдельная тонкость: знак процента в самом SQL нужно удваивать, иначе драйвер примет его за плейсхолдер:

WHERE is_active AND %(q)s <%% search_name

Миграции при старте

SEARCH_SCHEMA_SQL = [
    r"""ALTER TABLE companies ADD COLUMN IF NOT EXISTS search_name TEXT
        GENERATED ALWAYS AS (lower(regexp_replace(name, '^(ООО|АО|...)\s+', ''))) STORED""",
    """CREATE INDEX IF NOT EXISTS companies_search_prefix ON companies (search_name text_pattern_ops)""",
]

def ensure_schema() -> None:
    global SEARCH_SCHEMA_READY
    try:
        with db_pool.connection() as conn, conn.cursor() as cur:
            for stmt in SEARCH_SCHEMA_SQL:
                cur.execute(stmt)
        SEARCH_SCHEMA_READY = True
    except Exception as e:
        print(f"[АББ] не удалось применить миграцию: {e}", flush=True)

    for path, title in ((GROUPS_SQL_FILE, "группы компаний"),
                        (LIMITS_SQL_FILE, "лимиты и заявки"),
                        (RESERVES_SQL_FILE, "резервы РСБУ и МСФО")):
        if not path.is_file():
            continue
        try:
            with db_pool.connection() as conn, conn.cursor() as cur:
                cur.execute(path.read_text(encoding="utf-8"))
        except Exception as e:
            print(f"[АББ] миграция «{title}» не применилась: {e}", flush=True)

Это прямое следствие ошибки, описанной в лекции 3: скрипты из db/ выполняются только на пустом томе. Теперь схема доводится до нужного состояния при каждом запуске. Работает благодаря идемпотентности.

r"""...""" — «сырая» строка: \s внутри останется как есть, а не будет принят Python за escape-последовательность.

5.6. Эндпоинт поиска

PREFIX_SQL = """
SELECT id, name, inn, kpp, industry, 1.0::float AS score
FROM companies
WHERE is_active AND search_name LIKE %(prefix)s
ORDER BY search_name USING ~<~
LIMIT %(limit)s
"""

FUZZY_SQL = """
SELECT id, name, inn, kpp, industry, word_similarity(%(q)s, search_name)::float AS score
FROM companies
WHERE is_active AND %(q)s <%% search_name
ORDER BY score DESC, name
LIMIT %(limit)s
"""

@app.get("/api/companies")
def search_companies(query: str = Query(..., alias="q", min_length=3), limit: int = 8):
    params = {"q": query.lower(), "prefix": f"{query.lower()}%", "limit": limit}

    rows = db_query(INN_SQL, params) if query[:1].isdigit() else db_query(PREFIX_SQL, params)

    if len(rows) < 3:
        seen = {r["id"] for r in rows}
        for r in db_query(FUZZY_SQL, params):
            if r["id"] not in seen:
                rows.append(r)
        rows = rows[:limit]

    return to_jsonable(rows)

Где это в коде: api/app/main.py:137 — тексты запросов; api/app/main.py:167 — обработчик search_companies.

Логика в три шага:

  1. Начинается с цифры — ищем по ИНН, иначе по названию. Дешёвая эвристика, экономящая запрос.
  2. Префиксный запрос — 0,08 мс.
  3. Нашлось меньше трёх — дополняем нечётким поиском (64 мс). Он дорогой, поэтому запускается редко.

seen = {r["id"] for r in rows} — множество (set). Проверка in в нём работает за константное время, в списке — за линейное.

Демонстрация: SQL-инъекция вживую

Классическая атака: вместо ИНН пользователь вводит ' OR '1'='1.

Склейка строк — так делать нельзя:

evil = "' OR '1'='1"
bad = f"SELECT count(*) FROM companies WHERE inn = '{evil}'"
cur.execute(bad)

запрос: SELECT count(*) FROM companies WHERE inn = '' OR '1'='1'
вернулось строк: 28   ← вся таблица вместо нуля

Параметризация — так правильно:

cur.execute("SELECT count(*) FROM companies WHERE inn = %s", (evil,))

запрос: SELECT count(*) FROM companies WHERE inn = %s   параметр: "' OR '1'='1"
вернулось строк: 0   ← как и должно быть

Что произошло. В первом случае кавычка из ввода закрыла строковый литерал, а дальнейший текст стал частью команды: условие превратилось в inn = '' OR '1'='1', а '1'='1' истинно всегда. Вернулись все 28 компаний.

Во втором случае драйвер отправляет текст запроса и значение раздельно. Для базы ' OR '1'='1 — это просто строка, которую надо сравнить с колонкой inn. Совпадений нет, ответ ноль.

Здесь это выглядит безобидно — вернулось на 28 строк больше. В реальности тем же приёмом вытаскивают чужие данные и удаляют таблицы. Правило простое: значение никогда не попадает в текст запроса, только через параметр.

5.7. Преобразование данных для JSON

def decimal_to_float(v):
    return float(v) if isinstance(v, Decimal) else v

def to_jsonable(rows: list[dict]) -> list[dict]:
    return [{k: decimal_to_float(v) for k, v in r.items()} for r in rows]

Postgres возвращает NUMERIC как Decimal — тип с точной арифметикой, который стандартный сериализатор JSON не умеет. Переводим во float на границе API.

Компромисс осознанный: во float теоретически возможна потеря точности на больших суммах. Для отображения это несущественно, но вычисления должны оставаться в базе, где тип NUMERIC. Считать деньги во float в Python — плохая идея.

Даты тоже требуют внимания:

r["valid_until"] = r["valid_until"].isoformat() if r["valid_until"] else None

isoformat() даёт "2027-01-01" — строку, понятную и JSON, и JavaScript.

5.8. Группировка на стороне API

База возвращает плоские строки, интерфейсу нужна структура. Собираем её в API:

blocks = [
    {
        "code": code,
        "title": title,
        "items": [r for r in rows if r["block"] == code],
    }
    for code, title in BLOCK_TITLES.items()
]
return {
    "blocks": [b for b in blocks if b["items"]],
    "unified": {"sublimit": total, "utilized": used, "available": total - used},
    "applications": applications,
    "total": total,
    "used": used,
}

Почему здесь, а не в браузере: форма ответа — часть контракта API. Любой клиент (браузер, мобильное приложение, отчётный скрипт) получит одинаковую структуру и не будет повторять логику группировки.

Обратите внимание на unified — «единый сублимит» считается, а не хранится:

total = sum(r["limit_amount"] for r in rows)

Это прямое следствие определения из глоссария: единый сублимит есть совокупность лимитов клиента. Хранили бы отдельно — рано или поздно разошлось бы со слагаемыми.

5.9. Кэш: как подключать необязательную зависимость

class Cache:
    def __init__(self, url: str | None):
        self.enabled = False
        self._r = None
        if not url:
            return
        try:
            import redis
            self._r = redis.Redis.from_url(url, socket_timeout=0.3)
            self._r.ping()
            self.enabled = True
        except Exception as e:
            log.warning("Redis недоступен, работаем без кэша: %s", e)

    def get(self, key: str):
        if not self.enabled:
            return None
        try:
            raw = self._r.get(key)
            return json.loads(raw) if raw else None
        except Exception:
            return None

Приём — graceful degradation: если Redis не задан или недоступен, приложение работает без него, а не падает. Каждый метод проверяет enabled и глушит ошибки. Кэш — ускоритель, а не условие работы; ошибка в нём не должна ронять запрос.

socket_timeout=0.3 обязателен: без него недоступный Redis подвесит запрос на десятки секунд.

Лекция 6. Развёртывание: Docker, Compose и эксплуатация

6.1. Зачем контейнеры

Без них запуск проекта выглядит так: поставьте Python нужной версии, PostgreSQL, создайте базу, пользователя, поставьте пакеты, пропишите пути… На другой машине половина шагов сработает иначе.

Контейнер — коробка, в которой лежит программа вместе со всем окружением: нужной версией Python, библиотеками, настройками. Коробка запускается одинаково на любой машине с Docker.

Два понятия, которые путают:

  • Образ (image) — шаблон, «слепок» файловой системы. Только для чтения.
  • Контейнер (container) — запущенный экземпляр образа. Их может быть много из одного образа.

Аналогия: образ — класс, контейнер — объект.

Контейнер не виртуальная машина: он использует ядро хоста и потому стартует за секунды и почти ничего не весит сверх самой программы.

6.2. Dockerfile — рецепт образа

FROM python:3.12-slim

WORKDIR /srv
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY app ./app
COPY scripts ./scripts

EXPOSE 8000
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]

Построчно:

  • FROM python:3.12-slim — базовый образ. slim — урезанный, без лишних пакетов: меньше вес и меньше уязвимостей.
  • WORKDIR /srv — рабочая папка внутри контейнера.
  • ENV PYTHONUNBUFFERED=1 — не буферизовать вывод, чтобы логи появлялись сразу.
  • COPY requirements.txt . затем RUN pip install — порядок важен. Каждая инструкция создаёт слой, который кэшируется. Зависимости копируются отдельно от кода: правка кода не заставляет переустанавливать пакеты. Скопируй мы всё сразу — каждая правка означала бы полную переустановку.
  • EXPOSE 8000 — документирует порт (сам по себе ничего не открывает).
  • CMD [...] — команда запуска.

--host 0.0.0.0 обязателен: 127.0.0.1 внутри контейнера означает «только внутри контейнера», снаружи достучаться не выйдет.

6.3. docker-compose.yml — оркестровка

Compose описывает несколько сервисов и их связи в одном файле.

services:
  db:
    image: postgres:16-alpine
    container_name: abb-db
    environment:
      POSTGRES_USER: ${POSTGRES_USER:-abb}
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-abb}
      POSTGRES_DB: ${POSTGRES_DB:-abb}
    volumes:
      - ./db:/docker-entrypoint-initdb.d:ro
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5433:5432"
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${POSTGRES_USER:-abb} -d ${POSTGRES_DB:-abb}"]
      interval: 5s
      timeout: 3s
      retries: 10

Разбор:

Где это в коде: docker-compose.yml:7 — сервис db; docker-compose.yml:20 — его healthcheck; docker-compose.yml:26 — сервис api; docker-compose.yml:49 — профиль full у необязательных сервисов.

image vs build. Postgres берём готовым образом, API собираем из своего Dockerfile (build: ./api).

environment. Переменные окружения внутри контейнера. ${VAR:-default} — взять из .env, иначе значение по умолчанию.

volumes. Два разных вида:

  • ./db:/docker-entrypoint-initdb.d:ro — bind mount: папка хоста видна внутри контейнера. :ro — только чтение. Правки на хосте сразу видны внутри.
  • pgdata:/var/lib/postgresql/data — named volume: хранилище, управляемое Docker. Живёт независимо от контейнера. Именно поэтому данные не пропадают при docker compose down — и именно поэтому файлы из db/ не применяются повторно (см. ниже).

ports: "5433:5432". Слева порт хоста, справа порт контейнера. Postgres внутри слушает 5432, наружу отдаём 5433, чтобы не конфликтовать с локально установленным Postgres.

healthcheck. Команда проверки готовности. Без неё API стартует раньше базы и падает на первом запросе.

  api:
    build: ./api
    environment:
      DATABASE_URL: postgresql://${POSTGRES_USER:-abb}:${POSTGRES_PASSWORD:-abb}@db:5432/${POSTGRES_DB:-abb}
      REDIS_URL: ${REDIS_URL:-}
      WEB_DIR: /srv/web
    volumes:
      - ./api/app:/srv/app:ro
      - ./web:/srv/web:ro
      - ./db:/srv/db:ro
    depends_on:
      db: { condition: service_healthy }
    ports:
      - "8000:8000"

@db:5432 — внутри сети Compose сервисы видны по именам. Никаких IP-адресов: db — это имя сервиса, Docker резолвит его сам.

depends_on с condition: service_healthy — ждать не запуска контейнера, а именно готовности базы (по healthcheck).

Монтирование кода. ./api/app:/srv/app:ro означает, что правки в Python подхватываются перезапуском контейнера без пересборки образа. То же для web/: правка CSS видна после F5. В продакшене так не делают — код кладут в образ.

Профили — необязательные сервисы:

  cache:
    image: redis:7-alpine
    profiles: ["full"]

docker compose up                    # только db + api (2 образа)
docker compose --profile full up     # ещё nginx и redis

Мы сделали это после того, как nginx не скачался из-за таймаута к Docker Hub: чем меньше образов нужно тянуть, тем меньше поводов не запуститься.

6.4. Главная ловушка Postgres в Docker

- ./db:/docker-entrypoint-initdb.d:ro

Файлы из этой папки выполняются только один раз — при создании пустого тома. База уже существует → скрипты игнорируются молча.

Мы на этом потеряли время: добавили 03_search_index.sql, перезапустили, получили column "search_name" does not exist. Файл был на месте, но Postgres его не выполнял.

Три способа жить с этим:

  1. Пересоздать том (потеряв данные): docker compose down -v && docker compose up
  2. Накатить руками: docker compose exec -T db psql -U abb -d abb < db/03_search_index.sql
  3. Применять при старте API — наш путь, ensure_schema(). Требует идемпотентных миграций, зато нельзя забыть.

-v в down -v удаляет тома. Это необратимо.

6.5. nginx как обратный прокси

server {
    listen 80;
    root /usr/share/nginx/html;

    location = /index.html {
        add_header Cache-Control "no-store, must-revalidate";
    }
    location / {
        try_files $uri $uri/ /index.html;
    }
    location /api/ {
        proxy_pass http://api:8000/api/;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}

Обратный прокси — сервер, принимающий запросы и переправляющий их дальше. Браузер обращается к одному адресу, а за ним стоят несколько сервисов.

Зачем: статику nginx отдаёт быстрее Python, а /api/ и статика оказываются на одном origin — тогда не нужен CORS.

CORS — правило браузера: страница с localhost:8080 по умолчанию не может обращаться к localhost:8000, это разные origin. Обходится либо заголовками на сервере (CORSMiddleware у нас включён), либо тем, что всё живёт на одном адресе — как здесь.

try_files $uri $uri/ /index.html — искать файл, потом папку, иначе отдать index.html. Нужно для одностраничных приложений с маршрутизацией.

В базовом варианте nginx не нужен: FastAPI сам раздаёт web/ через StaticFiles, и всё живёт на 8000.

Демонстрация: что показывает /api/health, когда база падает

Всё работает:

curl -s localhost:8000/api/health

{"status": "ok", "db": true, "search_schema": true, "cache": false,
 "web_dir": "/srv/web", "web_mounted": true}

$ поиск -> 200

Останавливаем базу на ходу (docker compose stop db) и повторяем:

{"status": "degraded", "db": false, "search_schema": true, "cache": false,
 "web_dir": "/srv/web", "web_mounted": true}

В логах API при этом:

discarding closed connection: <psycopg.Connection [BAD] at 0x7f46b6fa9040>

Как это читать. status стал degraded, db: false — база недоступна. Но search_schema и web_mounted остались true: это состояние, узнанное при старте, оно не зависит от текущей доступности базы. Сервис отвечает, отдаёт фронтенд и честно сообщает, что именно сломалось.

Отдельное поведение — если база недоступна в момент запуска:

psycopg_pool.PoolTimeout: pool initialization incomplete after 30 sec

API не поднимается вовсе. Это сознательный выбор: db_pool.wait(timeout=30) в lifespan не даёт стартовать сервису, который заведомо не сможет работать. Лучше упасть сразу и заметно, чем принимать запросы и отвечать на каждый ошибкой. В Compose это дополнительно подстраховано healthcheck у базы и depends_on: condition: service_healthy у API.

1. Чем образ отличается от контейнера?

Показать ответ

Показать ответ

7. Чем bind mount отличается от named volume?

Показать ответ

Bind mount (./web:/srv/web) показывает папку хоста внутри контейнера — правки видны сразу. Named volume (pgdata:) — хранилище под управлением Docker, живущее независимо от контейнера.

Показать ответ

Сервер, принимающий запросы и переправляющий их дальше. nginx отдаёт статику быстрее Python и держит фронтенд с API на одном origin, благодаря чему не нужен CORS.

Показать ответ

127.0.0.1 внутри контейнера означает «только внутри этого контейнера». Снаружи, включая проброшенный порт, достучаться не выйдет.

10. Сервер отдаёт новый код, а на экране старый интерфейс. Что делать?

Показать ответ

Это кэш браузера: Cmd/Ctrl + Shift + R. Убедиться, что сервер действительно отдаёт новое, помогает bash tools/check_deploy.sh — он показывает содержимое контейнера и подключённые скрипты.

Показать ответ

const SearchBar = (() => {
  const input = document.getElementById('searchInput');
  const dropdown = document.getElementById('suggestionList');
  const submitButton = document.getElementById('searchButton');

  let suggestions = [];
  let selectedCompany = null;
  let requestCounter = 0;
  let debounceTimer = null;

  const callbacks = { submit: () => {} };

  input.addEventListener('input', () => {
    const text = input.value.trim();
    clearTimeout(debounceTimer);
    if (text.length < 3) { dropdown.classList.remove('is-open'); return; }
    debounceTimer = setTimeout(() => loadSuggestions(text), 160);
  });

  async function loadSuggestions(text) {
    const requestId = ++requestCounter;
    const result = await API.searchCompanies(text);
    if (requestId !== requestCounter) return;      // ответ устарел
    suggestions = result;
    render();
  }

  function render() {
    dropdown.innerHTML = suggestions.map((company, i) => `
      <div class="suggestion" data-index="${i}">
        <span class="suggestion-name">${company.name}</span>
        <span class="suggestion-meta">ИНН ${company.inn}</span>
      </div>`).join('');

    dropdown.querySelectorAll('.suggestion').forEach(node => {
      node.addEventListener('mousedown', event => {
        event.preventDefault();
        selectCompany(suggestions[+node.dataset.index]);
      });
    });

    dropdown.classList.add('is-open');
  }

  function selectCompany(company) {
    selectedCompany = company;
    input.value = company.name;
    dropdown.classList.remove('is-open');
    submitButton.disabled = false;
  }

  submitButton.addEventListener('click', () => {
    if (selectedCompany) callbacks.submit(selectedCompany);
  });

  return { onSubmit: fn => { callbacks.submit = fn; } };
})();

Разберём стыки построчно:

  1. getElementById('searchInput') ← id из шага 3.
  2. API.searchCompanies ← модуль из шага 5.
  3. dropdown.classList.add('is-open') ← класс из шага 4.
  4. data-index="${i}" — кладём номер в разметку, читаем через node.dataset.index. + перед ним превращает строку в число: атрибуты всегда строки.
  5. callbacks.submit — модуль не знает, что произойдёт после нажатия. Он объявляет событие, а решение принимает app.js. Это инверсия зависимостей: поиск не зависит от дерева вкладок.

Часть II. Как слои связаны: четыре шва

Полезнее помнить не файлы, а швы — места, где слои соприкасаются. Их ровно четыре, и каждый ломается по-своему.

Шов 1: HTML ↔ CSS (класс)

Шов 2: HTML ↔ JS (идентификатор)

Ломается громко: null, а следом Cannot read properties of null. Частая причина — скрипт выполнился до появления элемента.

Ломается видимо: 404 (не тот путь), 422 (не тот параметр), 500 (упал сервер). Диагностика: вкладка Network в браузере — там виден и запрос, и ответ.

Тонкость: совпадать должны не только адреса, но и имена полей в ответе. API отдаёт limit_amount — интерфейс читает item.limit_amount. Переименуете поле в SQL — получите undefined в таблице, без единой ошибки.

Ломается громко: UndefinedColumn, UndefinedTable. Наш случай: column "search_name" does not exist, потому что миграция не применилась.
